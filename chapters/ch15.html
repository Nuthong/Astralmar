Control Variable Scope and Logic Using Code Blocks

15.1 ทำไมต้องเข้าใจ Scope ของตัวแปร

คำสั่งแตกสาขาและคำสั่งวนซ้ำใช้ code block รวมกลุ่มบรรทัดโค้ดที่ควรถูกรัน ข้าม หรือวนซ้ำ แต่นั่นไม่ใช่หน้าที่เดียวของ code block — code block ยังใช้ควบคุม/จำกัดการเข้าถึงตัวแปรได้ ด้วย scope ของตัวแปรหมายถึงส่วนของแอปที่ตัวแปรนั้นเข้าถึงได้ การเข้าใจว่า code block มีผลต่อ scope ของตัวแปรยังไง เป็นเรื่องสำคัญมากในการเขียนโปรแกรม

สมมติคุณทำงานกับแอปขนาดใหญ่ที่ใช้ nested iteration และ selection statement ประมวลผลข้อมูล ใน array แอปของคุณใช้ตัวแปรช่วยทำงานหลายอย่างทั่วทั้งแอป ตัวแปรบางตัวทำหน้าที่เดียวกันใน หลายส่วนของแอป และคุณพยายามใช้ชื่อตัวแปรซ้ำ พอแอปโตขึ้น คุณเริ่มเจอผลลัพธ์การคำนวณที่ไม่คาด คิด และ error ที่บอกว่าตัวแปรยังไม่ถูกกำหนดค่าหรือไม่มีอยู่จริง — คุณต้องปรับปรุงวิธีประกาศ และเข้าถึงตัวแปร และต้องเข้าใจเรื่อง scope ให้ลึกซึ้งขึ้น

ในบทนี้ คุณจะประกาศตัวแปรเพื่อใช้ทั้งข้างในและข้างนอกขอบเขตของ code block คุณจะตัด code block ออกในบางสถานการณ์เพื่อให้โค้ดอ่านง่ายขึ้น และเรียนว่า code block มีผลต่อการ เข้าถึงและมองเห็นตัวแปรยังไง

15.2 ลงมือ: Code Block กับ Scope ของตัวแปร

code block คือคำสั่ง C# หนึ่งบรรทัดขึ้นไปที่นิยามเส้นทางการทำงาน คำสั่งที่อยู่ นอก code block มีผลต่อว่า code block นั้นจะถูกรันเมื่อไร รันไหม และรันบ่อยแค่ไหนตอนรันจริง ขอบเขตของ code block มักถูกกำหนดด้วยปีกกา {}

นอกจากมีผลต่อเส้นทางการทำงานแล้ว code block ยังมีผลต่อ scope ของตัวแปรด้วย — scope ของตัวแปรหมายถึงการมองเห็นของตัวแปรนั้นต่อโค้ดส่วนอื่นในแอป ตัวแปรที่มี scope แบบ local เข้าถึงได้แค่ข้างใน code block ที่มันถูกนิยามไว้เท่านั้น ถ้าพยายามเข้าถึงตัวแปร นอก code block นั้น จะได้ compiler error

เตรียมโปรเจกต์

Terminal 
dotnet new console -o ch15-scope

สร้างตัวแปรข้างใน Code Block

Program.cs 
bool flag = true;
if (flag)
{
    int value = 10;
    Console.WriteLine($"Inside the code block: {value}");
}
Output
Inside the code block: 10

พยายามเข้าถึงตัวแปรนอก Code Block

Program.cs
bool flag = true;
if (flag)
{
    int value = 10;
    Console.WriteLine($"Inside the code block: {value}");
}
Console.WriteLine($"Outside the code block: {value}");
Output
Program.cs(7,46): error CS0103: The name 'value' does not exist in the current context

error นี้เกิดขึ้นเพราะตัวแปรที่ประกาศข้างใน code block เข้าถึงได้ (มองเห็นได้) แค่ข้างใน code block นั้นเท่านั้น เพราะไม่สามารถเข้าถึง value นอก code block ที่มัน ถูกประกาศได้ จึงเข้าถึงจากบรรทัดที่ 7 ไม่ได้

ℹ️ Local Variable ตัวแปรที่ประกาศไว้ใน code block ของเมธอด เรียกว่า local variable — คุณอาจเจอคำนี้ บ่อยเวลาอ่านบทความที่พูดถึงเรื่อง variable scope

ย้ายการประกาศตัวแปรขึ้นไปเหนือ Code Block

ถ้าต้องการเข้าถึงตัวแปรทั้งข้างในและข้างนอก code block ต้องประกาศตัวแปรไว้ก่อน (เหนือ) code block เพื่อให้โค้ดข้างนอก "มองเห็น" ตัวแปรได้:

Program.cs
bool flag = true;
int value;

if (flag)
{
    Console.WriteLine($"Inside the code block: {value}");
}

value = 10;
Console.WriteLine($"Outside the code block: {value}");
Output
Program.cs(6,49): error CS0165: Use of unassigned local variable 'value'

ยัง error อยู่ดี! คราวนี้ error มาจากบรรทัดข้างใน code block เพราะ value ยังไม่ถูกกำหนดค่า (ทบทวน error นี้ได้จาก บทที่ 2) ถ้าบรรทัด value = 10; อยู่เหนือ code block ของ if แอปจะคอมไพล์ผ่าน ปกติ แต่เพราะ value ยังไม่ถูกกำหนดค่า จึงเข้าถึงข้างใน code block ไม่ได้

กำหนดค่าเริ่มต้นตอนประกาศตัวแปร

Program.cs 
bool flag = true;
int value = 0;

if (flag)
{
    Console.WriteLine($"Inside the code block: {value}");
}

value = 10;
Console.WriteLine($"Outside the code block: {value}");
Output
Inside the code block: 0
Outside the code block: 10

โค้ดนี้แก้ error "unassigned local variable" ได้ด้วยการกำหนดค่า value ตอน ประกาศ (initialize) เลย

คอมไพเลอร์ตีความโค้ดยังไง — จุดที่ต้องระวัง

เพื่อช่วยป้องกัน runtime error คอมไพเลอร์ C# วิเคราะห์โค้ดของคุณอย่างละเอียด แต่บางครั้ง คอมไพเลอร์ก็ตีความโค้ดต่างจากที่คุณคิด ลองเทียบโค้ด 2 ชุดนี้ที่ดูเหมือนจะทำหน้าที่เดียวกัน:

ชุดที่ 1
bool flag = true;
int value;

if (flag)
{
    value = 10;
    Console.WriteLine($"Inside the code block: {value}");
}

Console.WriteLine($"Outside the code block: {value}");
ชุดที่ 2
int value;

if (true)
{
    value = 10;
    Console.WriteLine($"Inside the code block: {value}");
}

Console.WriteLine($"Outside the code block: {value}");
🛑 ชุดที่ 1 compile ไม่ผ่าน แต่ชุดที่ 2 ผ่าน! ทำไม? สำหรับชุดที่ 1 คอมไพเลอร์ตีความว่า flag เป็นตัวแปร bool ที่อาจ เป็น true หรือ false ก็ได้ คอมไพเลอร์จึงสรุปว่าถ้า flag เป็น false value จะไม่ถูกกำหนดค่าเลยตอน Console.WriteLine() บรรทัดสุดท้าย ทำงาน — คอมไพเลอร์มองเห็น 2 เส้นทางที่เป็นไปได้ (ถ้า flag=true กับถ้า flag=false) และเส้นทางหลังทำให้เกิด error จึงฟ้อง error ทันที (พร้อมขีดเส้นหยักแดงใต้ value ใน editor)

สำหรับชุดที่ 2 คอมไพเลอร์สรุปว่าเนื้อหาใน code block ของ if (true) จะถูกรันเสมอ (เพราะ true เป็น true ตายตัว ไม่มีทาง เปลี่ยนแปลง) คอมไพเลอร์จึงมองว่ามีแค่เส้นทางเดียวที่เป็นไปได้ ไม่มี error
💡 บทเรียนสำคัญ คอมไพเลอร์ C# วิเคราะห์ "เส้นทางการทำงานที่เป็นไปได้ทั้งหมด" (definite assignment analysis) ไม่ใช่แค่เดาว่าคุณตั้งใจให้เกิดอะไรขึ้น — ถ้ามีเส้นทางไหนที่ตัวแปรอาจยังไม่ถูกกำหนดค่า คอมไพเลอร์จะฟ้อง error ทันที แม้ในทางปฏิบัติเส้นทางนั้นจะไม่มีวันเกิดขึ้นจริงก็ตาม (เช่นถ้าคุณรู้ว่า flag จะเป็น true เสมอ) — วิธีแก้ที่ปลอดภัยที่สุดคือ initialize ตัวแปรเสมอ ตอนประกาศ (แบบหัวข้อ 15.2e)

Check ★ นักพัฒนาเขียนโค้ดที่มี if code block โดย initialize ตัวแปร int ตัวแรกเป็น 5 เหนือ code block เงื่อนไข if เป็น true ถ้าตัว แรกมีค่ามากกว่า 0 บรรทัดแรกในบล็อก initialize ตัวแปร int ตัวที่สองเป็น 6 บรรทัดที่สอง ในบล็อกกำหนดผลบวกของทั้งสองตัวให้ตัวแรก บรรทัดแรกหลังบล็อกแสดงค่าตัวแรก ผลลัพธ์คืออะไร?

  • Aไม่ error และแสดงค่า = ผลบวกของตัวแปรทั้งสอง
  • Bไม่ error และแสดงค่าเริ่มต้นจากก่อนเข้าบล็อก
  • Cerror เพราะตัวแปรตัวแรกไม่อยู่ใน scope หลังจบบล็อก
เฉลย: ข้อ A. ตัวแปรตัวแรกถูกประกาศเหนือ code block จึงมี scope ครอบคลุมทั้งข้างในและข้างนอก (ไม่ error แบบข้อ C) และค่าที่แสดงหลังบล็อกคือค่าล่าสุด ที่ถูกกำหนด (คือผลบวก 5+6=11) ไม่ใช่ค่าเริ่มต้นก่อนเข้าบล็อก (ข้อ B ผิด)

15.3 ลงมือ: ตัด Code Block ออกจาก if เพื่อความอ่านง่าย

นักพัฒนาชอบเขียนโค้ดที่ประหยัดการพิมพ์และพื้นที่ โดยไม่เสียความอ่านง่าย — ใช้หลัก "น้อยแต่มาก" เฉพาะตอนที่มันทำให้กระบวนการพัฒนาอ่านและเข้าใจง่ายขึ้นเท่านั้น

ถ้า code block มีแค่บรรทัดเดียว บางทีก็ไม่จำเป็นต้องนิยาม code block แบบเป็นทางการด้วยปีกกา เลยก็ได้ แม้ในทางเทคนิคจะไม่ต้องแยกบรรทัดด้วยซ้ำ แต่การรวมหลายคำสั่งไว้บรรทัดเดียวมักทำให้ โค้ดอ่านยาก

ตัวอย่าง if ที่มี Code Block

Program.cs 
bool flag = true;
if (flag)
{
    Console.WriteLine(flag);
}
Output
True

ตัดปีกกาออก

code block นี้มีแค่บรรทัดเดียว จึงมีตัวเลือกตัดปีกกาออกได้:

Program.cs 
bool flag = true;
if (flag)
    Console.WriteLine(flag);
Output
True
ℹ️ ตัดปีกกาไม่ได้เปลี่ยนความหมาย แม้ตัดปีกกาออก Console.WriteLine(flag); ก็ยังเป็น code block ของ if statement นั้นเหมือนเดิม — แค่ 2 บรรทัดสั้นลง และตราบใดที่บรรทัดข้างใต้ if ยังเยื้อง (indent) อยู่ โค้ดก็ยังอ่านง่ายเหมือนเดิม

ระวัง: รวมทุกอย่างไว้บรรทัดเดียวอาจทำให้อ่านยากขึ้น

เพราะทั้ง if และ Console.WriteLine() สั้น อาจถูกล่อใจให้รวม ไว้บรรทัดเดียว — ไวยากรณ์ C# อนุญาตให้ทำแบบนี้ได้:

Program.cs (ไม่แนะนำ)
bool flag = true;
if (flag) Console.WriteLine(flag);

ผลลัพธ์เหมือนเดิม แต่ลองนึกภาพโค้ดแบบนี้อยู่ในไฟล์ใหญ่ๆ ที่มีโค้ดรอบข้างเยอะๆ การรวม คำสั่งแบบนี้อาจทำให้อ่านยากขึ้นมาก Microsoft แนะนำแนวทางนี้เวลาทำ if ที่มี code block บรรทัดเดียว:

  • อย่าใช้รูปแบบบรรทัดเดียวเด็ดขาด เช่น if (flag) Console.WriteLine(flag);
  • ใช้ปีกกาได้เสมอ (ไม่ผิด) และบังคับต้องใช้ถ้า code block ใดใน if/else if/.../else ใช้ปีกกา หรือถ้าคำสั่งเดียวยาวคร่อมหลายบรรทัด
  • ละปีกกาได้ก็ต่อเมื่อทุก code block ใน if/else if/.../else เดียวกัน อยู่ในบรรทัดเดียวทั้งหมด (ต้องสม่ำเสมอ)

ตัวอย่างกับเชน if-elseif-else

Program.cs — อ่านยาก 
string name = "steve";
if (name == "bob") Console.WriteLine("Found Bob");
else if (name == "steve") Console.WriteLine("Found Steve");
else Console.WriteLine("Found Chuck");
Output
Found Steve

โค้ดรันได้ แต่แน่นและอ่านยาก ลองจัดใหม่ให้แต่ละคำสั่งขึ้นบรรทัดใหม่:

Program.cs — อ่านง่ายขึ้นมาก 
string name = "steve";

if (name == "bob")
    Console.WriteLine("Found Bob");
else if (name == "steve") 
    Console.WriteLine("Found Steve");
else
    Console.WriteLine("Found Chuck");

สังเกตว่าอ่านง่ายขึ้นมากแค่ไหน — นี่คือตัวอย่างที่ดีของ "ละปีกกาแต่คงความอ่านง่ายไว้" ตามที่แนวทางแนะนำ

15.4 ท้าทาย: แก้โค้ดที่มีปัญหาเรื่อง Scope

โจทย์ตามต้นฉบับ MS Learn

โค้ดนี้เขียนได้ไม่ดี มีปัญหาซ่อนอยู่หลายจุด ให้คุณใช้ความรู้เรื่อง code block และ variable scope แก้ไข:

Program.cs — โค้ดตั้งต้น (มีปัญหา)
int[] numbers = { 4, 8, 15, 16, 23, 42 };

foreach (int number in numbers)
{
    int total;

    total += number;

    if (number == 42)
    {
       bool found = true;

    }

}

if (found) 
{
    Console.WriteLine("Set contains 42");

}

Console.WriteLine($"Total: {total}");

ผลลัพธ์ที่ต้องได้หลังแก้ไข:

ผลลัพธ์เป้าหมาย
Set contains 42
Total: 108

อาจต้องปรับเรื่อง scope ของตัวแปร และปรับให้อ่านง่ายขึ้นด้วย (ควรได้ประมาณ 17 บรรทัด)

💡 ขอคำใบ้

ลองไล่หาปัญหาทีละจุด: total ประกาศไว้ที่ไหน initialize หรือยัง? found ประกาศไว้ที่ไหน เข้าถึงได้จากนอก if (found) ไหม? ปีกกาที่มี code block บรรทัดเดียวจำเป็นต้องมีไหม?

🔓 ดูเฉลย
Program.cs — เฉลย 
int[] numbers = { 4, 8, 15, 16, 23, 42 };
int total = 0;
bool found = false;

foreach (int number in numbers)
{
    total += number;
    if (number == 42)
        found = true;
}

if (found)
    Console.WriteLine("Set contains 42");

Console.WriteLine($"Total: {total}");
Output
Set contains 42
Total: 108

การเปลี่ยนแปลงหลักที่แก้ปัญหาโค้ดเดิม:

  • ย้ายการประกาศตัวแปร total และ found ออกมาไว้ นอก foreach statement — เดิม total ถูกประกาศข้างใน foreach ทำให้ถูกสร้างใหม่ (และ reset) ทุกรอบของลูป ส่วน found ถูก ประกาศไว้ข้างใน if (number == 42) ซ้อนอยู่ 2 ชั้น เข้าถึงจากนอก foreach ไม่ได้เลย (นี่คือสาเหตุที่โค้ดเดิม error CS0103 ตอนเช็ค if (found))
  • กำหนดค่าเริ่มต้นให้ทั้ง total และ found ด้วยค่าที่ สมเหตุสมผล (0 และ false) — แก้ error CS0165 จากตัวแปรที่ยังไม่ initialize
  • ตัด code block (ปีกกา) ออกจาก if ที่มีแค่บรรทัดเดียว เพื่อความ อ่านง่าย

CS0103: The name '...' does not exist in the current context พยายามเข้าถึงตัวแปรที่ scope อยู่แค่ในอีก code block หนึ่ง — ย้ายการประกาศตัวแปร ขึ้นไปเหนือ code block ที่ต้องการให้เข้าถึงได้ทั้งคู่
CS0165: Use of unassigned local variable ประกาศตัวแปรไว้นอก block แล้ว แต่ยังไม่ initialize — กำหนดค่าเริ่มต้นให้เสมอตอน ประกาศ (ทบทวนที่ บทที่ 2)
ตัวแปรสะสม (เช่น sum) รีเซ็ตทุกรอบของ loop โดยไม่ตั้งใจ ประกาศตัวแปรไว้ข้างใน code block ของ loop โดยไม่ตั้งใจ — ต้องประกาศไว้นอก loop เสมอถ้าต้องการให้ค่าคงอยู่ข้ามรอบ (ทบทวนที่ บทที่ 10 และ บทที่ 12)
คอมไพล์ไม่ผ่านทั้งที่ "ดูแล้วน่าจะเข้าเงื่อนไขเสมอ" คอมไพเลอร์วิเคราะห์ทุกเส้นทางที่เป็นไปได้ตามชนิดข้อมูล (เช่น bool อาจเป็น true หรือ false) ไม่ได้เดาเจตนาของคุณ — initialize ตัวแปรเสมอเพื่อความปลอดภัย
เชน if-elseif-else อ่านยากเพราะยัดทุกอย่างไว้บรรทัดเดียว ตัดปีกกาได้ แต่ต้องขึ้นบรรทัดใหม่เสมอสำหรับ code block — อย่ารวม if กับ คำสั่งไว้บรรทัดเดียวกัน (Microsoft แนะนำห้ามใช้รูปแบบนี้เด็ดขาด)

15.6 ❓ Knowledge Check

คำถามชุดนี้แปลจาก Microsoft Learn (1 ข้อฝังในเนื้อหา + 3 ข้อ Module Assessment — ข้อ 2 กับ 3 เป็นโจทย์หลอกที่ต้องไล่โค้ดในหัวอย่างละเอียด ลองคิดเองก่อนดูเฉลย)

1. ข้อใดถูกต้องเกี่ยวกับการแสดง/ตัดปีกกาของ code block ใน if statement?

  • Aตัดปีกกาออกจาก else if และ else ไม่ได้
  • Bถ้าตัดปีกกาออกจาก if-elseif-else ต้องตัด whitespace ออกด้วย
  • Cเลือกสไตล์ที่เพิ่มความอ่านง่ายเสมอ
เฉลย: ข้อ C. นี่คือหลักการภาพรวมที่คลุมทุกกรณี — ข้อ A ผิดเพราะ ตัดปีกกาจาก else if/else ได้เหมือนกัน (ตราบใดที่ทุก block ในเชนเดียวกันอยู่บรรทัดเดียว) ข้อ B ผิดเพราะการตัด whitespace เป็นคนละเรื่องกับการตัดปีกกา (ดูตัวอย่างหัวข้อ 15.3 ที่ตัดปีกกาแต่เพิ่มการขึ้นบรรทัดใหม่กลับเข้าไป)

2. ตัวแปรตัวแรก initialize เป็น 1 เหนือ if code block เงื่อนไขเป็น true ถ้าตัวแรก > 0 บรรทัดแรกในบล็อก initialize ตัวแปรตัวที่สองเป็น 8 บรรทัดที่สองในบล็อกกำหนดผลบวกทั้งสองให้ตัวแรก บรรทัดแรกหลังบล็อกแสดงค่าตัวแรก ผลลัพธ์คืออะไร?

  • Aไม่ error และแสดงค่า 9
  • Bไม่ error และแสดงค่า 1
  • Cerror เพราะตัวแรกไม่อยู่ใน scope หลังจบบล็อก
เฉลย: ข้อ A (แสดงค่า 9). ตัวแรกประกาศเหนือบล็อก จึง scope ครอบคลุม ทั้งสองฝั่ง (ไม่ error) และค่าที่แสดงคือค่าล่าสุดหลังบวกกัน (1+8=9) ไม่ใช่ค่าตั้งต้น (ข้อ B ผิด)

3. ตัวแปรตัวแรก initialize เป็น 5 เหนือ if code block เงื่อนไขเป็น true ถ้าตัวแรก > 0 บรรทัดแรกในบล็อก initialize ตัวแปรตัวที่สองเป็น 6 (ตัวที่สองประกาศข้างในบล็อกเท่านั้น) บรรทัดแรกหลังบล็อกเอาตัวที่สองไปบวก กับตัวแรก บรรทัดที่สองหลังบล็อกแสดงค่าตัวแรก ผลลัพธ์คืออะไร?

  • Aไม่ error และแสดงค่า 11
  • Berror เกิดที่บรรทัดแสดงค่าตัวแรก
  • Cbuild error เกิดที่บรรทัดบวกตัวแปรทั้งสอง
เฉลย: ข้อ C. จุดต่างจากข้อ 2 คือตัวที่สองถูกประกาศข้างใน บล็อก scope ของมันจึงจำกัดอยู่แค่ในนั้น พอบรรทัด "บวกตัวแปรทั้งสอง" อยู่นอกบล็อก แต่พยายามอ้างอิงตัวที่สอง จะได้ error CS0103 ทันทีตอน build — ไม่ใช่ error ที่บรรทัดแสดงผล (ข้อ B ผิดตำแหน่ง) และไม่ใช่กรณีไม่ error (ข้อ A ผิด)

15.7 ✍️ แบบฝึกหัดท้ายบท

ข้อ 1ง่าย

โค้ดนี้ error หาสาเหตุและแก้ไข:

Program.cs (ผิด)
bool isReady = true;
if (isReady)
{
    string message = "พร้อมแล้ว";
}
Console.WriteLine(message);
ดูเฉลย

message scope อยู่แค่ในบล็อก if ต้องย้ายการประกาศออกมาไว้นอกบล็อก (พร้อม initialize):

Program.cs (ถูก)
bool isReady = true;
string message = "";
if (isReady)
{
    message = "พร้อมแล้ว";
}
Console.WriteLine(message);
ข้อ 2ง่าย

ตัดปีกกาออกจากโค้ดนี้ (มีแค่บรรทัดเดียวต่อ block) พร้อมคงการขึ้นบรรทัดใหม่ไว้:

Program.cs (ก่อนแก้)
int score = 85;
if (score >= 80)
{
    Console.WriteLine("ผ่าน");
}
else
{
    Console.WriteLine("ไม่ผ่าน");
}
ดูเฉลย
Program.cs (หลังแก้)
int score = 85;
if (score >= 80)
    Console.WriteLine("ผ่าน");
else
    Console.WriteLine("ไม่ผ่าน");
ข้อ 3ง่าย

โค้ดนี้ compile ไม่ผ่าน หาสาเหตุ (ใบ้: ไม่ใช่ปัญหาเรื่อง scope แต่เป็นปัญหาเรื่อง initialize):

Program.cs (ผิด)
bool ready = true;
int count;

if (ready)
{
    Console.WriteLine(count);
}

count = 5;
ดูเฉลย

error CS0165 — count ถูกใช้ข้างใน code block ก่อนที่จะถูก กำหนดค่า (บรรทัด count = 5; อยู่หลัง code block) ต้องย้ายการกำหนดค่า ขึ้นไปก่อน หรือ initialize ตอนประกาศเลย เช่น int count = 0;

ข้อ 4กลาง

โค้ดนี้ compile ผ่าน (ไม่ error) ทั้งที่ดูคล้ายข้อ 3 มาก อธิบายว่าทำไมถึงต่างกัน:

Program.cs
int count;

if (true)
{
    count = 5;
    Console.WriteLine(count);
}
ดูเฉลย

ตรงกับหลักการจากหัวข้อ 15.2f — เงื่อนไขเป็น true ตัวอักษรตรงๆ (ไม่ใช่ ตัวแปร bool) คอมไพเลอร์จึงรู้แน่นอนว่า code block นี้จะถูกรันเสมอ มีเส้นทาง การทำงานเดียวเท่านั้น (ไม่มีทางที่ count จะไม่ถูกกำหนดค่าตอนถึงบรรทัด Console.WriteLine(count)) จึงไม่ error

ข้อ 5กลาง

เขียนโค้ดวนหา array int[] temps = { 28, 31, 35, 29, 33 }; นับว่ามีกี่วัน ที่อุณหภูมิเกิน 30 องศา ใช้ตัวแปรนับที่ scope ถูกต้อง (ไม่รีเซ็ตทุกรอบ) และตัดปีกกา ออกจาก if ที่มีบรรทัดเดียวด้วย

ดูเฉลย
Program.cs
int[] temps = { 28, 31, 35, 29, 33 };
int hotDays = 0;

foreach (int temp in temps)
    if (temp > 30)
        hotDays++;

Console.WriteLine($"มี {hotDays} วันที่เกิน 30 องศา");

สังเกตว่าตัดปีกกาได้ทั้งชั้น foreach และชั้น if ที่ซ้อนกัน เพราะแต่ละชั้น มีแค่คำสั่งเดียวข้างใน

ข้อ 6ท้าทาย

โค้ดนี้มีบั๊กเรื่อง scope ซ่อนอยู่ 2 จุด (คล้ายโจทย์ท้าทายหัวข้อ 15.4 แต่เป็นสถานการณ์ใหม่) หาให้เจอและแก้ไข ให้ได้ผลลัพธ์ คะแนนรวม: 15, พบเลข 7: True

Program.cs (มีบั๊ก)
int[] scores = { 3, 5, 7 };

foreach (int score in scores)
{
    int sum;
    sum += score;

    if (score == 7)
    {
        bool foundSeven = true;
    }
}

Console.WriteLine($"คะแนนรวม: {sum}, พบเลข 7: {foundSeven}");
ดูเฉลย

บั๊กทั้งสองจุดเหมือนโจทย์หัวข้อ 15.4 เป๊ะ: sum ต้องย้ายออกมานอก foreach พร้อม initialize เป็น 0 · foundSeven ต้องย้ายออกมานอกทั้ง foreach และ if พร้อม initialize เป็น false:

Program.cs (ถูก)
int[] scores = { 3, 5, 7 };
int sum = 0;
bool foundSeven = false;

foreach (int score in scores)
{
    sum += score;
    if (score == 7)
        foundSeven = true;
}

Console.WriteLine($"คะแนนรวม: {sum}, พบเลข 7: {foundSeven}");

📌 สรุปบทที่ 15

เป้าหมายของบทนี้คือเข้าใจว่า code block มีผลต่อการเข้าถึงตัวแปรยังไง และต้องทำอะไรบ้างเพื่อ ให้แน่ใจว่าตัวแปรมี scope ที่เหมาะสม ถูก initialize และเข้าถึงได้เมื่อจำเป็นในแอป คุณสำรวจ ผลของการประกาศตัวแปรทั้งข้างในและข้างนอกขอบเขตของ code block และผลของการ initialize ตัวแปรที่มีต่อการเข้าถึง รวมถึงวิธีที่การตัด code block ที่ไม่จำเป็นออก มีผลต่อความอ่านง่าย ของโค้ด

โค้ดที่ใช้ตัวแปร scope ผิดหรือยังไม่ initialize จะทำให้เกิด error ตอนคอมไพล์หรือรัน ความสามารถในการกำหนด scope และ initialize ตัวแปรได้ถูกต้อง จะช่วยให้ผู้ใช้แอปของคุณได้ ประสบการณ์ที่ดีขึ้น

Cheat Sheet — บทที่ 15
