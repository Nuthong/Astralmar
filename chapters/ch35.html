35.1 สถานการณ์ที่ต้องใช้ Exception Handling

ข้อผิดพลาดตอน runtime ในแอป C# ถูกจัดการด้วยกลไกที่เรียกว่า exception — exception ให้วิธีจัดการปัญหาที่เป็นระบบ สม่ำเสมอ และตรวจสอบชนิดได้ ทั้งสำหรับปัญหาระดับระบบและ ระดับแอปพลิเคชัน exception ถูกสร้างโดย .NET runtime เองหรือโดยโค้ดในแอปก็ได้

สถานการณ์เขียนโปรแกรมที่มักต้องใช้ exception handling ได้แก่:

  • รับ input จากผู้ใช้ — เช่น ค่าที่กรอกมาผิดรูปแบบหรือเกินขอบเขต
  • ประมวลผลข้อมูลและคำนวณ — เช่น หารด้วยศูนย์ cast ผิดชนิด กำหนดค่าที่เกินขอบเขต
  • อ่าน/เขียนไฟล์ — เช่น ไฟล์ไม่มีอยู่จริง ไม่มีสิทธิ์เข้าถึง หรือไฟล์ถูกโปรแกรมอื่น ใช้งานอยู่
  • ทำงานกับฐานข้อมูล — เช่น การเชื่อมต่อหลุด syntax ผิดใน SQL หรือละเมิด constraint
  • สื่อสารผ่านเครือข่าย — เช่น การเชื่อมต่อหลุด timeout หรือเซิร์ฟเวอร์ปลายทางตอบ error กลับมา
  • ทรัพยากรภายนอกอื่นๆ — เช่น Web Service, REST API หรือไลบรารีของผู้อื่น

35.2 ลงมือ: try-catch พื้นฐานตัวแรก

เตรียมโปรเจกต์

Terminal 
dotnet new console -o ch35-exceptions

คำสั่งของ exception handling ใน C# คือ try, catch และ finally แต่ละคำสั่งมี code block ของตัวเอง และทำหน้าที่ต่างกัน:

โครงสร้าง
try
{
   // try code block - โค้ดที่อาจก่อ exception
}
catch
{
   // catch code block - โค้ดจัดการ exception
}
finally
{
   // finally code block - โค้ดเก็บกวาดทรัพยากร
}

try block คือโค้ดที่ "อาจ" ก่อ exception ถ้าโค้ดใน try ก่อ exception ขึ้นจริง catch block ที่ตรงกันจะจัดการมัน — จะจัดการ (handle) บันทึก (log) หรือเพิกเฉย (ignore) ก็ได้ ส่วน finally block จะรันเสมอไม่ว่า จะเกิด exception หรือไม่ก็ตาม มักใช้เก็บกวาดทรัพยากรที่จองไว้ใน try

ลองพิมพ์โค้ดนี้ลงใน Program.cs:

Program.cs 
double float1 = 3000.0;
double float2 = 0.0;
int number1 = 3000;
int number2 = 0;

Console.WriteLine(float1 / float2);
Console.WriteLine(number1 / number2);
Console.WriteLine("Exit program");
Output
∞
Unhandled exception. System.DivideByZeroException: Attempted to divide by zero.
   at Program.<Main>$(String[] args) in Program.cs:line 6

สังเกตว่าหาร double ด้วยศูนย์ไม่เกิด exception เลย — ได้ผลลัพธ์เป็น ∞ (infinity) ตามกฎ IEEE 754 แต่หาร int ด้วยศูนย์เกิด DivideByZeroException ทันที และทำให้แอปปิดตัวก่อนจะพิมพ์ "Exit program" ด้วยซ้ำ — ไม่ได้แปลว่าควรใช้ double แทน int เสมอ แค่ ต้องใช้ชนิดข้อมูลที่เหมาะสมกับงาน แล้วเขียน exception handling ดักปัญหาที่อาจเกิดขึ้น

ล้อมสองบรรทัดคำนวณด้วย try:

Program.cs 
double float1 = 3000.0;
double float2 = 0.0;
int number1 = 3000;
int number2 = 0;

try
{
    Console.WriteLine(float1 / float2);
    Console.WriteLine(number1 / number2);
}

Console.WriteLine("Exit program");

โค้ดนี้จะขึ้นเส้นหยักสีแดงใต้วงเล็บปิดของ try — เพราะไวยากรณ์ C# บังคับว่า ต้องมี catch หรือ finally ตามหลัง try เสมอ ใส่ catch block เข้าไป:

Program.cs 
double float1 = 3000.0;
double float2 = 0.0;
int number1 = 3000;
int number2 = 0;

try
{
    Console.WriteLine(float1 / float2);
    Console.WriteLine(number1 / number2);
}
catch
{
    Console.WriteLine("An exception has been caught");
}

Console.WriteLine("Exit program");
Output
∞
An exception has been caught
Exit program

แม้ exception จะยังเกิดขึ้นอยู่ แต่ตอนนี้แอปทำงานจนจบได้แล้ว — exception handling ทำให้ ควบคุมการทำงานของโค้ดได้เมื่อเกิด exception และช่วยให้โค้ดเสถียรและให้ผลลัพธ์ตามที่คาดหวัง

Check ★ code block ใดที่ "ต้อง" รันเสมอไม่ว่าจะเกิด exception หรือไม่?

  • Atry
  • Bcatch
  • Cfinally
เฉลย: ข้อ C. try คือโค้ดที่อาจก่อปัญหา catch รันเฉพาะตอนเกิด exception เท่านั้น ส่วน finally รันเสมอ ไม่ว่าผลจะเป็นอย่างไร มักใช้เก็บกวาดทรัพยากร

35.3 กระบวนการค้นหา catch: Call Stack Unwinding

เวลาเกิด exception .NET runtime จะค้นหา catch ที่ใกล้ที่สุดที่จัดการ exception นั้นได้ เริ่มจาก method ที่ทำให้เกิด exception ก่อน ถ้าโค้ดนั้นไม่ได้อยู่ใน try block หรืออยู่แต่ catch จัดการไม่ได้ runtime จะค้นหาต่อไป ยัง method ที่เรียก method ปัจจุบันมา ไล่ขึ้นไปเรื่อยๆ จนกว่าจะเจอ catch ที่ จัดการได้ — ถ้าไม่เจอเลยตลอดทาง runtime จะปิดแอปและแสดง error ให้ผู้ใช้เห็น

ก่อนถ่ายโอนการทำงานไปยัง catch block runtime จะรัน finally block ทุกอันที่เกี่ยวข้องกับ try ที่เจอระหว่างทางค้นหาก่อนเสมอ (เรียงจาก ใกล้จุดเกิด exception ที่สุดก่อน) ลองดูตัวอย่าง try-finally ที่ซ้อนอยู่ใน try-catch:

ตัวอย่าง
try
{
    // ขั้น 1: เริ่มทำงาน
    try
    {
        // ขั้น 2: เกิด exception ตรงนี้
    }
    finally
    {
        // ขั้น 4: ระบบรัน finally ของ try ที่เกิด exception ก่อน
    }
}
catch // ขั้น 3: ระบบเจอ catch ที่จัดการ exception ได้
{
    // ขั้น 5: ระบบส่งการทำงานไปที่บรรทัดแรกของ catch นี้
}

สังเกตลำดับ: exception เกิดใน try ชั้นใน (ขั้น 2) → runtime เจอ catch ของ try ชั้นนอก (ขั้น 3) → ก่อนจะกระโดดไปที่ catch จริงๆ ต้องรัน finally ของ try ชั้นในก่อน (ขั้น 4) → แล้วค่อยเข้า catch (ขั้น 5) ในตัวอย่างนี้ทุกอย่างอยู่ใน method เดียว แต่ในความเป็นจริง try-catch และ try-finally อาจกระจาย อยู่คนละ method ที่เรียกต่อกันเป็นทอดๆ ก็ได้

Call Stack คืออะไร

ลองนึกภาพ call stack เหมือนหอคอยบล็อกไม้ — เริ่มจากบล็อกเดียว ทุกครั้งที่วางบล็อก เพิ่ม จะวางทับบนบล็อกเดิม ตอนแอปเริ่มรันในตัว debugger จุดเริ่มต้นแอป (top-level statements ซึ่ง VS Code เรียกว่า method Main) คือบล็อกชั้นแรกของหอคอย ทุกครั้งที่ method หนึ่งเรียก method อื่น method ใหม่จะถูกวางซ้อนบนสุด พอโค้ดออกจาก method นั้น มันจะถูกเอาออกจาก stack

call stack unwinding คือกระบวนการที่ .NET runtime ใช้ตอนเจอ error — เหมือนตอน ต้องถอดบล็อกออกจากหอคอย เริ่มจากบล็อกบนสุดไล่ถอดลงมาทีละชั้นจนกว่าจะถึงชั้นที่ต้องการ — runtime ก็ถอด call layer ออกจาก stack ไล่จากบนสุดจนกว่าจะเจอ method ที่มี catch จัดการ exception นั้นได้

35.4 Exception ที่พบบ่อยจาก .NET Runtime

exception ถูกสร้างโดย .NET runtime หรือโดยโค้ดในโปรแกรม ชนิดของ exception ขึ้นอยู่กับ โค้ดที่ทำให้เกิด exception นั้น ต่อไปนี้คือ exception พื้นฐานที่ runtime โยนเมื่อการทำงาน ระดับล่างสุดล้มเหลว:

Exceptionเกิดเมื่อ
ArrayTypeMismatchExceptionพยายามเก็บ element ผิดชนิดลงใน array
DivideByZeroExceptionพยายามหารค่า integer ด้วยศูนย์
FormatExceptionรูปแบบของ argument ไม่ถูกต้อง
IndexOutOfRangeExceptionเข้าถึง index ของ array/collection ที่อยู่นอกขอบเขต
InvalidCastExceptionการแปลงชนิด (explicit conversion) ล้มเหลวตอน runtime
NullReferenceExceptionพยายามเข้าถึง member ของ object ที่เป็น null
OverflowExceptionการคำนวณใน checked context ได้ผลลัพธ์เกินขอบเขตชนิดข้อมูล

ตัวอย่างโค้ดที่ทำให้เกิดแต่ละ exception:

DivideByZeroException
int number1 = 3000;
int number2 = 0;
Console.WriteLine(number1 / number2); // เกิด DivideByZeroException
FormatException
string userValue = "two";
int valueEntered = int.Parse(userValue); // เกิด FormatException
IndexOutOfRangeException
int[] values1 = { 3, 6, 9, 12, 15, 18, 21 };
int[] values2 = new int[6];
values2[values1.Length - 1] = values1[values1.Length - 1]; // เกิน bound ของ values2
NullReferenceException
string? lowCaseString = null;
Console.WriteLine(lowCaseString.ToUpper()); // เกิด NullReferenceException
OverflowException
decimal x = 400;
byte i;
checked
{
    i = (byte)x; // เกิด OverflowException เพราะ byte เก็บได้แค่ 0-255
}
ℹ️ checked context คืออะไร ปกติการแปลงชนิด integral (เช่น int เป็น byte) จะ "ตัดปัดค่า ทิ้งเงียบๆ" โดยไม่แจ้งเตือน (unchecked context) แต่ถ้าล้อมด้วย checked { } การแปลงที่เกินขอบเขตจะโยน OverflowException แทน ช่วยดักจับข้อผิดพลาดที่ อาจถูกมองข้ามได้

Check ★ โค้ด string? s = null; s.ToUpper(); จะเกิด exception ชนิดใด?

  • AFormatException
  • BNullReferenceException
  • CInvalidCastException
เฉลย: ข้อ B. การเรียก method บน object ที่เป็น null (ในที่นี้คือเรียก .ToUpper() บน string ที่เป็น null) ทำให้เกิด NullReferenceException เสมอ

35.5 ลงมือ: จับ Exception เจาะจงชนิด + อ่าน Property

exception ทุกตัวคือ instance ของคลาสที่สืบทอดมาจาก System.Exception — คลาส ลูกส่วนใหญ่ไม่ได้เพิ่มอะไรใหม่ แค่สืบทอดจาก Exception เฉยๆ ดังนั้นรู้จัก property ของคลาส Exception ก็เข้าใจ exception ส่วนใหญ่ได้แล้ว:

Propertyใช้ทำอะไร
Messageรายละเอียดของสาเหตุ exception (ใช้บ่อยที่สุด)
StackTraceลำดับการเรียก method + บรรทัดที่เกิดปัญหา ใช้หาต้นตอ
InnerExceptionเก็บ exception ก่อนหน้าไว้เป็นชุด ถ้าเกิดซ้อนกัน
Sourceชื่อแอปหรือ object ที่ทำให้เกิด error
Dataเก็บข้อมูลเสริมแบบ key-value
HResultรหัสตัวเลขที่ผูกกับ exception ชนิดนั้นๆ
HelpLinkURL ไปหน้าช่วยเหลือเกี่ยวกับ exception นี้
TargetSitemethod ที่เป็นต้นตอ throw exception นี้

ลองอัปเดตโค้ดให้เรียก method ที่เรียกต่อกันเป็นทอด:

Program.cs 
try
{
    Process1();
}
catch
{
    Console.WriteLine("An exception has occurred");
}

Console.WriteLine("Exit program");

static void Process1()
{
    WriteMessage();
}

static void WriteMessage()
{
    double float1 = 3000.0;
    double float2 = 0.0;
    int number1 = 3000;
    int number2 = 0;

    Console.WriteLine(float1 / float2);
    Console.WriteLine(number1 / number2);
}
Output
∞
An exception has occurred
Exit program

WriteMessage() ถูกเรียกจาก Process1() ซึ่งถูกเรียกจาก top-level statements — exception เกิดขึ้นในระดับที่ลึกกว่า try-catch ถึง สอง method แต่ก็ยังถูกจัดการได้ เพราะ call stack unwinding ไล่ค้นหาขึ้นไปเรื่อยๆ ตามที่ อธิบายในหัวข้อก่อน

ปรับ Process1 ให้จับ exception เองแทน แล้วอ่านค่า Message:

Program.cs (ปรับ Process1) 
static void Process1()
{
    try
    {
        WriteMessage();
    }
    catch (Exception ex)
    {
        Console.WriteLine($"Exception caught in Process1: {ex.Message}");
    }
}

catch (Exception ex) จับ Exception เก็บไว้ในตัวแปรชื่อ ex แล้วใช้ ex.Message แสดง error ออกทางคอนโซล แม้ catch เฉยๆ (ไม่ระบุชนิด) จะเขียนได้ แต่ไม่แนะนำ เพราะจะจับทุกชนิด exception ปนกันหมด แยกแยะไม่ออก — ควรจับเฉพาะ exception ที่โค้ดของคุณรู้วิธีแก้ไขจริงๆ เท่านั้น และระบุชนิดให้เจาะจงที่สุดเท่าที่ทำได้

เปลี่ยนเป็นจับเฉพาะ DivideByZeroException:

Program.cs 
static void Process1()
{
    try
    {
        WriteMessage();
    }
    catch (DivideByZeroException ex)
    {
        Console.WriteLine($"Exception caught in Process1: {ex.Message}");
    }
}

ผลลัพธ์เหมือนเดิม แต่ตอนนี้ Process1 จะจับเฉพาะชนิดที่มันเตรียมรับมือ ไว้เท่านั้น ลองแก้ WriteMessage ให้เกิด exception คนละชนิด:

Program.cs 
static void WriteMessage()
{
    double float1 = 3000.0;
    double float2 = 0.0;
    int number1 = 3000;
    byte smallNumber;

    Console.WriteLine(float1 / float2);
    checked
    {
        smallNumber = (byte)number1; // number1 = 3000 เกินขอบเขต byte (0-255)
    }
}
Output
∞
An exception has occurred
Exit program

คราวนี้ catch (DivideByZeroException ex) ใน Process1 จับ OverflowException ไม่ได้ (คนละชนิดกัน) exception จึงไหลต่อขึ้นไปให้ catch ทั่วไปที่ top-level statements จัดการแทน — นี่คือพฤติกรรมที่ต้องการ: จับเฉพาะ exception ที่โค้ดพร้อมรับมือจริงๆ เท่านั้น

Check ★ ทำไมควรจับ exception แบบเจาะจงชนิด (เช่น DivideByZeroException) แทนที่จะใช้ catch (Exception ex) ทั่วไปเสมอ?

  • Aเพราะ catch ทั่วไปทำให้โปรแกรมช้าลง
  • Bเพื่อจับเฉพาะ exception ที่โค้ดรู้วิธีแก้ไขจริงๆ ไม่ปนกับชนิดอื่นที่ไม่ได้เตรียมรับมือ
  • Cเพราะ catch ทั่วไปใช้กับ int ไม่ได้
เฉลย: ข้อ B. การระบุชนิดเจาะจงช่วยไม่ให้โค้ด "กลืน" exception ชนิดอื่นที่มันไม่รู้วิธีแก้ไปโดยไม่ตั้งใจ — exception ที่ไม่เกี่ยวข้องควรไหลต่อไปให้ catch ระดับที่เหมาะสมกว่าจัดการแทน

35.6 จับหลาย Exception พร้อมกันในบล็อกเดียว

ถ้าเกิด exception ตัวแรกในบล็อกแล้ว บรรทัดถัดไปที่อาจก่อ exception ตัวที่สองจะไม่ถูก รันเลย การทำงานกระโดดไป catch ทันทีที่เจอ exception ตัวแรก — ถ้าอยากให้ แต่ละบรรทัดเสี่ยงถูกจัดการแยกกัน ต้องแยก try-catch ของตัวเองให้แต่ละส่วน:

Program.cs 
static void WriteMessage()
{
    double float1 = 3000.0;
    double float2 = 0.0;
    int number1 = 3000;
    int number2 = 0;
    byte smallNumber;

    try
    {
        Console.WriteLine(float1 / float2);
        Console.WriteLine(number1 / number2);
    }
    catch (DivideByZeroException ex)
    {
        Console.WriteLine($"Exception caught in WriteMessage: {ex.Message}");
    }

    checked
    {
        try
        {
            smallNumber = (byte)number1;
        }
        catch (OverflowException ex)
        {
            Console.WriteLine($"Exception caught in WriteMessage: {ex.Message}");
        }
    }
}

แต่ไม่ใช่ทุกสถานการณ์ที่ควรทำแบบนี้ — ถ้างานส่วนที่สองต้องพึ่งผลลัพธ์จากส่วนแรกที่ทำ สำเร็จ (เช่น ขั้นตอนที่ 2 ของกระบวนการต้องใช้ผลจากขั้นตอนที่ 1) การปล่อยให้โค้ดทำงานต่อ ทั้งที่ขั้นแรกล้มเหลวอาจทำให้เกิดปัญหาซ้อนปัญหา บางครั้งควรแจ้งผู้ใช้ตรงๆ ว่าขั้นตอนแรก ล้มเหลว แล้วไม่พยายามทำขั้นตอนที่เหลือต่อเลยจะดีกว่า

อีกสถานการณ์คือข้อมูลหลายชุดที่อาจก่อ exception คนละชนิดกัน ในลูปเดียว — ใช้หลาย catch เรียงจากเจาะจงไปหากว้างได้:

Program.cs 
string[] inputValues = new string[] { "three", "9999999999", "0", "2" };

foreach (string inputValue in inputValues)
{
    int numValue = 0;
    try
    {
        numValue = int.Parse(inputValue);
        Console.WriteLine($"แปลงสำเร็จ: {numValue}");
    }
    catch (FormatException)
    {
        Console.WriteLine("รูปแบบไม่ถูกต้อง กรุณากรอกตัวเลข");
    }
    catch (OverflowException)
    {
        Console.WriteLine("ตัวเลขที่กรอกใหญ่หรือเล็กเกินไป");
    }
    catch (Exception ex)
    {
        Console.WriteLine(ex.Message);
    }
}
Output
รูปแบบไม่ถูกต้อง กรุณากรอกตัวเลข
ตัวเลขที่กรอกใหญ่หรือเล็กเกินไป
แปลงสำเร็จ: 0
แปลงสำเร็จ: 2

catch แต่ละอันจับคนละชนิด: "three" ไม่ใช่ตัวเลขเลย → FormatException "9999999999" เป็นตัวเลขแต่ใหญ่เกิน int รับได้ → OverflowException ส่วน "0" กับ "2" แปลงสำเร็จปกติ สังเกตว่า catch (Exception ex) ทั่วไปต้อง อยู่ล่างสุดเสมอ — ถ้าสลับให้ catch ทั่วไปอยู่บนสุด โค้ดจะคอมไพล์ไม่ผ่าน เพราะ catch ที่เจาะจงกว่าจะกลายเป็น "unreachable" (ไปไม่ถึงเพราะโดนดักไปก่อนแล้ว)

35.7 ⚠️ กับดักที่พบบ่อย

อาการสาเหตุ / วิธีแก้
เขียน catch (Exception ex) ไว้บล็อกเดียวจับทุกอย่าง ใช้ได้เป็น "ตาข่ายรองรับ" ชั้นนอกสุด แต่ควรมี catch เจาะจงชนิดก่อนเสมอสำหรับ exception ที่รู้วิธีแก้ไขจริง ไม่งั้นจะแยกไม่ออกว่าเกิดปัญหาอะไรกันแน่
คอมไพล์ error "a previous catch clause already catches all exceptions" เรียง catch ทั่วไป (catch (Exception ex)) ไว้บนสุด ต้องย้ายไปไว้ล่างสุดเสมอ — catch เจาะจงชนิดต้องมาก่อน catch กว้างๆ
โค้ดหลัง exception ตัวแรกใน try block ไม่ถูกรันเลย พฤติกรรมปกติ — พอเกิด exception การทำงานกระโดดไป catch ทันที ถ้าอยากให้แต่ละ บรรทัดเสี่ยงถูกจัดการแยกกัน ต้องแยก try-catch ของตัวเอง (ดูหัวข้อ 35.6)
catch จับ exception ไว้เฉยๆ ไม่ทำอะไรเลย (empty catch) อันตราย — ทำให้ปัญหาจริงถูกซ่อนเงียบๆ อย่างน้อยควรพิมพ์หรือบันทึก ex.Message ไว้เสมอ เพื่อให้รู้ว่าเกิดอะไรขึ้น
ใช้ double หวังเลี่ยง DivideByZeroException ไปเลยทุกที่ double หารศูนย์ได้ผล infinity/NaN ไม่ throw จริง แต่ไม่ได้แปลว่าควรเปลี่ยน ชนิดข้อมูลทุกจุดเพื่อหนี exception — เลือกชนิดข้อมูลตามความเหมาะสมของงาน แล้ว จัดการ exception ให้ถูกวิธีแทน

📌 สรุปบทที่ 35

บทนี้พาคุณลงมือเขียน exception handling จริงด้วย try, catch และ finally คุณเห็นว่า .NET runtime ค้นหา catch ที่เหมาะสม อย่างไรผ่านกระบวนการ call stack unwinding รู้จัก exception พื้นฐานที่ runtime โยนบ่อยที่สุด (DivideByZeroException, NullReferenceException, IndexOutOfRangeException ฯลฯ) และฝึก จับ exception แบบเจาะจงชนิดพร้อมอ่าน property อย่าง Message เพื่อรายงาน ปัญหาให้ผู้ใช้เห็น

หลักการสำคัญที่สุดคือ: จับเฉพาะ exception ที่โค้ดรู้วิธีแก้ไขจริง เรียง catch จากเจาะจง ไปหากว้างเสมอ และอย่าปล่อยให้ catch block ว่างเปล่าซ่อนปัญหาไว้เงียบๆ บทถัดไปคุณจะได้ เรียนรู้อีกฝั่งหนึ่งของเหรียญ — การสร้างและโยน exception ของคุณเองด้วย throw
