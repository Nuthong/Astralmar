38.1 สเปกของ Challenge

โค้ดตั้งต้นของบทนี้คือแอปเครื่องคิดเงินตัวเดียวกับบทที่ 37 (ที่แก้บั๊ก "ทอนแบงก์ห้าผิด index" ไปแล้ว และมี exception handling ครบแล้ว) — แต่มีบั๊ก logic ใหม่อีกจุดซ่อนอยู่ ทำให้ ยอดลิ้นชักไม่ balance ในบางสถานการณ์ ตามสเปกนี้:

  • top-level statements จำลองธุรกรรมด้วยราคาสินค้าสุ่ม
  • สุ่มค่า itemCost ในช่วง 2-49
  • จำลองธุรกรรมทั้งหมด 100 รายการ
  • ผลลัพธ์ต้องมีข้อความ "Could not complete transaction: InvalidOperationException: Not enough money provided to complete the transaction." ปรากฏบ้าง
  • ผลลัพธ์ต้องมีข้อความ "Could not complete transaction: InvalidOperationException: The till is unable to make change for the cash provided." ปรากฏบ้าง
  • เป้าหมายสุดท้าย: ยอด "reported" กับ "expected" ต้องเท่ากันเป๊ะ หลังรันครบ 100 ธุรกรรม
💡 ลองก่อนดูเฉลย บทนี้ไม่มีคำแนะนำทีละขั้นเหมือนบทที่ 37 แล้ว — ลองใช้ทักษะ debugger ทั้งหมดจากบทที่ 34, 37 (breakpoint, Step Into/Over, VARIABLES, safety check) ไล่หาเองก่อน แล้วค่อยเปิดดูเฉลยที่ ซ่อนไว้ท้ายบท

38.2 โค้ดตั้งต้น (มีบั๊กซ่อนอยู่)

เตรียมโปรเจกต์ใหม่ (แยกจากบทที่ 37):

Terminal 
dotnet new console -o ch38-challenge

คัดลอกโค้ดฉบับสมบูรณ์จากบทที่ 37 มาวางใน Program.cs แล้วปรับตามสเปกใหม่นี้ เท่านั้น:

Program.cs (จุดที่ต้องปรับ) 
bool useTestData = true; // เริ่มด้วย true ก่อนเสมอ เพื่อยืนยัน baseline

// ...

int transactions = 100; // เดิม 40

// ...

int itemCost = valueGenerator.Next(2, 50); // ช่วงเดิมตามสเปก (คงไว้เหมือนบทที่ 37)

อย่าลืมแก้ launch.json เป็น "console": "integratedTerminal" เหมือนทุกครั้งที่แอปมี Console.ReadLine()

38.3 ลงมือ: ยืนยัน Baseline ด้วย testData

ก่อนไล่หาบั๊ก ต้องยืนยันก่อนว่า testData ยังทำงานถูกต้องอยู่ (ค่า useTestData = true) รันแอปด้วย debugger แล้วดูบรรทัดท้ายผลลัพธ์ — ยอด "reported" กับ "expected" ควรตรงกันเป๊ะเหมือนบทที่ 37

ถ้ายอดตรงกัน แปลว่าบั๊กใหม่ที่ซ่อนอยู่ (ถ้ามี) จะไม่แสดงตัวเมื่อใช้ testData — สอดคล้องกับสเปกที่บอกว่าปัญหาปรากฏเฉพาะตอนใช้ข้อมูลสุ่มจำนวนมากเท่านั้น

38.4 เปิดใช้ข้อมูลสุ่ม 100 รายการ

เปลี่ยน useTestData เป็น false บันทึกแล้วรันใหม่ — ตรวจสอบว่า ผลลัพธ์ตรงตามสเปกครบทุกข้อ:

  • มีบันทึกธุรกรรมครบ 100 รายการ
  • มีข้อความ "Not enough money provided" ปรากฏอย่างน้อยหนึ่งครั้ง
  • มีข้อความ "unable to make change" ปรากฏอย่างน้อยหนึ่งครั้ง
  • ยอด "reported" กับ "expected" ท้ายผลลัพธ์ไม่ตรงกัน (นี่คือสัญญาณของบั๊กที่ต้องหา)

38.5 ใช้ Debugger หาบั๊ก

ใช้กระบวนการเดียวกับบทที่ 37 ทุกประการ:

  1. ตั้ง breakpoint บนบรรทัด Console.WriteLine(); เปล่าๆ ท้ายแต่ละรอบของ while loop หลัก
  2. Start Debugging แล้วกด Continue ไปเรื่อยๆ จนกว่ายอด reported/expected จะเริ่ม ไม่ตรงกัน
  3. สังเกตรายละเอียดธุรกรรมรอบที่เกิดปัญหา — เงินที่รับมาถูกต้องไหม? เงินทอนที่คืนถูกต้อง ไหม? ลิ้นชักขาด/เกินเท่าไหร่?
  4. ธนบัตรชนิดที่ขาดหายไปคือเบาะแสสำคัญที่สุด — ไล่ดู while loop ของธนบัตร ชนิดนั้นใน MakeChange ทีละบรรทัด

Check ★ ทำไม testData ถึงไม่เจอบั๊กที่ซ่อนอยู่ ทั้งที่โค้ดจุดนั้นถูกเรียกจริงหรือเปล่าก็ยังไม่รู้?

  • Aเพราะชุด testData ที่ออกแบบไว้อาจไม่เคยทำให้เงื่อนไขของ while loop จุดที่มีบั๊กเป็นจริงเลยสักครั้ง
  • Bเพราะ testData ปิด exception handling ไปโดยอัตโนมัติ
  • Cเพราะ debugger ทำงานกับ testData ไม่ได้
เฉลย: ข้อ A. ถ้า while loop ที่มีบั๊กไม่เคยถูก "เข้าไปทำงานข้างใน" เลยสักครั้งกับชุดข้อมูลทดสอบ บั๊กก็ไม่มีทางแสดงตัวออกมา — นี่คือเหตุผลที่การทดสอบด้วย ข้อมูลหลากหลาย (โดยเฉพาะข้อมูลสุ่มจำนวนมาก) สำคัญกว่าการทดสอบด้วยชุดข้อมูลตายตัวเพียง อย่างเดียวเสมอ
💡 คำใบ้ 1 (เปิดถ้าติดจริงๆ)

ชุด testData ที่ใช้มาตลอด ({6, 10, 17, 20, 31, 36, 40, 41}) ไม่เคยทำให้ changeNeeded มากกว่า 19 เลยสักรายการ — ลองคำนวณด้วยมือดูว่า while loop ไหนใน MakeChange ที่ไม่เคยถูกเข้าไปทำงาน ข้างในเลยสักครั้งกับชุดข้อมูลนี้

💡 คำใบ้ 2 (เปิดถ้ายังติดอยู่)

ธนบัตรที่ไม่เคยถูกทดสอบเลยคือใบ $20 — ลองดูบล็อก while ที่ทอนแบงก์ยี่สิบ ในเมธอด MakeChange อย่างละเอียด เทียบ index ของ array ที่เงื่อนไข ใช้เช็ค กับ index ที่โค้ดข้างในบล็อกใช้ลดค่า — เหมือนกันไหม?

🔓 ดูเฉลย

บั๊กอยู่ในบล็อก while ที่ทอนแบงก์ยี่สิบ:

MakeChange (มีบั๊ก)
while ((changeNeeded > 19) && (cashTill[3] > 0))
{
    cashTill[2]--; // บั๊ก! ควรเป็น cashTill[3]-- (ลดจำนวนแบงก์สิบแทนแบงก์ยี่สิบ)
    changeNeeded -= 20;
    Console.WriteLine("\t A twenty");
}

เงื่อนไขเช็ค cashTill[3] (แบงก์ยี่สิบ) ถูกต้อง แต่ข้างในบล็อกกลับลดค่า cashTill[2] (แบงก์สิบ) แทน — พิมพ์ข้อความ "A twenty" ให้ลูกค้าเห็นถูกต้อง แต่ระบบหักแบงก์สิบออกจากลิ้นชักแทนแบงก์ยี่สิบจริงๆ ทำให้บัญชีไม่ตรงกัน เหมือนกับบั๊ก แบงก์ห้าในบทที่ 37 เป๊ะ เพียงแค่คนละธนบัตรและซ่อนลึกกว่าเพราะต้องมีเงื่อนไข changeNeeded > 19 เกิดขึ้นก่อนถึงจะเจอ ซึ่ง testData ไม่เคยทำให้เงื่อนไข นี้เป็นจริงเลย

แก้โดยเปลี่ยน index ให้ตรงกัน:

MakeChange (แก้แล้ว)
while ((changeNeeded > 19) && (cashTill[3] > 0))
{
    cashTill[3]--;
    changeNeeded -= 20;
    Console.WriteLine("\t A twenty");
}

38.6 ตรวจผลลัพธ์สุดท้าย

ลบ breakpoint ทั้งหมด รันแอปอีกครั้งด้วยข้อมูลสุ่ม 100 รายการ ยืนยันว่า:

  • มี 100 ธุรกรรมครบ
  • เห็นข้อความ exception ทั้งสองแบบปรากฏอย่างน้อยหนึ่งครั้ง
  • ยอด "reported" กับ "expected" ท้ายผลลัพธ์ตรงกันเป๊ะทุกครั้งที่รัน

38.7 ⚠️ กับดักที่พบบ่อย

อาการสาเหตุ / วิธีแก้
รันหลายครั้งแล้วบางครั้งยอด balance บางครั้งไม่ ปกติ — ข้อมูลสุ่มใหม่ทุกครั้งที่รัน เงื่อนไขที่ทำให้บั๊กแสดงตัว (เช่น changeNeeded > 19) อาจไม่เกิดขึ้นเลยในบางรอบที่โชคดี ลองรันหลายรอบเพื่อให้มั่นใจ ว่าแก้ครบจริง
หาบั๊กไม่เจอสักที ทั้งที่ step ผ่านทุกบรรทัดแล้ว ลองเทียบ "ธนบัตรที่ระบบพิมพ์ว่าทอนออกไป" กับ "ธนบัตรที่ array ถูกลดค่าจริง" ทีละ ธุรกรรม — บั๊กแบบนี้ซ่อนอยู่ตรงความไม่ตรงกันระหว่างสอง "เรื่องเล่า" นี้เสมอ
แก้บั๊กแล้วแต่ยอดยังไม่ balance เช็คว่าคัดลอกโค้ดจากบทที่ 37 มาครบทุกจุดจริง โดยเฉพาะการแก้บั๊กแบงก์ห้าที่ทำไปแล้ว — ถ้าลืมเอาการแก้เดิมมาด้วย จะเจอทั้งสองบั๊กพร้อมกัน สับสนได้ง่าย

38.8 ❓ Knowledge Check

1. วิธีใดช่วยยืนยันได้ดีที่สุดว่าเมธอดที่จัดการเงิน/ทรัพยากรทำงานถูกต้องจริง ไม่ใช่แค่ "ดูรันได้ไม่พัง"?

  • Aเช็คว่าไม่มี error สีแดงขึ้นตอนรัน
  • Bทำ safety check คำนวณผลลัพธ์ที่คาดไว้แยกต่างหาก แล้วเทียบกับผลจริง
  • Cเช็คว่าโค้ด compile ผ่าน
เฉลย: ข้อ B. เหมือนที่แอปเครื่องคิดเงินทำ — คำนวณ registerCheckTillTotal แยกต่างหากจาก cashTill แล้วเทียบกัน ท้ายสุด นี่คือวิธีเดียวที่จับบั๊ก "เงียบ" แบบในบทนี้ได้ ต่อให้โค้ด compile ผ่านและรันไม่ พังเลยก็ตาม

38.9 ✍️ แบบฝึกหัดท้ายบท

ข้อ 1กลาง

เขียนฟังก์ชันช่วยเทสต์ bool VerifyTillBalance(int reported, int expected) ที่คืน true ถ้าสองค่าตรงกัน และพิมพ์ข้อความเตือนพร้อมผลต่างถ้าไม่ตรงกัน ก่อนคืน false

ดูเฉลย
Program.cs
static bool VerifyTillBalance(int reported, int expected)
{
    if (reported == expected)
    {
        return true;
    }
    Console.WriteLine($"Till mismatch! reported={reported}, expected={expected}, diff={expected - reported}");
    return false;
}
ข้อ 2ยาก

ตั้งใจปลูกบั๊กแบบเดียวกัน (index ผิดใน while block) ไว้ในบล็อกทอนแบงก์หนึ่งดอลลาร์ (ones) แทน แล้วลองอธิบายว่าทำไมบั๊กจุดนี้ถึงง่ายกว่าที่จะถูกจับได้ด้วย testData เมื่อเทียบกับบั๊กแบงก์ยี่สิบในบทนี้

ดูแนวคำตอบ

แนวคำตอบตัวอย่าง: บล็อกทอนแบงก์หนึ่งดอลลาร์ถูกเข้าไปทำงานข้างในบ่อยมากในชุด testData (แทบทุกธุรกรรมที่มีเศษเป็นจำนวนคี่จะต้องทอนแบงก์หนึ่งอย่างน้อยหนึ่งใบ) ต่างจากบล็อกทอนแบงก์ยี่สิบที่ต้องการเงื่อนไข changeNeeded > 19 ซึ่ง testData ไม่เคยทำให้เป็นจริงเลย — ยิ่งโค้ดส่วนไหนถูกเรียกใช้บ่อยเท่าไหร่ (code coverage สูง) จากชุดทดสอบที่มีอยู่ โอกาสที่บั๊กในส่วนนั้นจะถูกจับได้เร็วก็ยิ่ง สูงตามไปด้วย

Trophy 1 ข้อผิดพลาดที่เกิดตอน build (เช่น syntax ผิด) เรียกว่าอะไร ต่างจาก exception อย่างไร?

  • Aเรียกว่า error — เกิดตอน build ไม่ใช่ตอน runtime แบบ exception
  • Bเรียกว่า exception เหมือนกัน แค่คนละชื่อ
  • Cไม่มีชื่อเรียกต่างกัน ใช้แทนกันได้เสมอ
เฉลย: ข้อ A. ทบทวนจากบทที่ 33

Trophy 2 ปุ่มใดบน Debug toolbar ใช้ "เข้าไปดูข้างใน" method ทีละบรรทัด?

  • AStep Over
  • BStep Into
  • CStep Out
เฉลย: ข้อ B. ทบทวนจากบทที่ 34

Trophy 3 catch (Exception ex) ทั่วไปควรวางอยู่ตำแหน่งไหนเมื่อมีหลาย catch ต่อกัน?

  • Aบนสุดเสมอ
  • Bล่างสุดเสมอ
  • Cตำแหน่งไหนก็ได้
เฉลย: ข้อ B. ทบทวนจากบทที่ 35 — ไม่งั้น compile ไม่ผ่านเพราะ catch เจาะจงกว่ากลายเป็น unreachable

Trophy 4 throw; กับ throw ex; ต่างกันอย่างไรตอน re-throw?

  • Athrow; รักษา StackTrace เดิมไว้ ส่วน throw ex; จะรีเซ็ต StackTrace ใหม่
  • Bทั้งสองแบบทำงานเหมือนกันทุกประการ ไม่มีความต่าง
  • Cthrow ex; เร็วกว่าเสมอ
เฉลย: ข้อ A. ทบทวนจากบทที่ 36

Trophy 5 "safety check" ในแอปเครื่องคิดเงินมีไว้ทำอะไร?

  • Aคำนวณยอดที่คาดไว้แยกต่างหาก เพื่อยืนยันว่า logic ของเมธอดหลักทำงานถูกต้อง
  • Bป้องกันไม่ให้แอปถูกแฮ็ก
  • Cเข้ารหัสข้อมูลลิ้นชักเงิน
เฉลย: ข้อ A. ทบทวนจากบทที่ 37 และ บทที่ 38
