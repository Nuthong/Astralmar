33.1 ทำไม "แก้บั๊ก" ไม่ใช่เรื่องเดียวกันไปหมด

นักพัฒนาทุกคนต้องผ่านสามกระบวนการที่มักถูกปนกันจนดูเหมือนเป็นเรื่องเดียวกัน คือ testing (การทดสอบ), debugging (การดีบัก) และ exception handling (การจัดการข้อยกเว้น) ทั้งสามอย่างเกี่ยวข้องกัน แต่ไม่ใช่สิ่งเดียวกัน และแต่ละอย่างก็มี ขอบเขตความรับผิดชอบต่างกัน บทนี้จะแยกให้ชัดว่าอันไหนคืออะไร ก่อนไปลงมือใช้เครื่องมือ debugger จริงในบทถัดไป

ข้อควรรู้ที่สำคัญก่อนอื่น: ข้อผิดพลาดที่เกิดตอนคอมไพล์/build (เช่น ลืมเซมิโคลอน พิมพ์ชื่อตัวแปรผิด) เรียกว่า error ธรรมดา — ไม่นับเป็นส่วนหนึ่งของกระบวนการ exception handling คำว่า exception ในหนังสือเล่มนี้หมายถึงเฉพาะข้อผิดพลาดที่เกิด ตอนแอปพลิเคชันกำลังรัน (runtime) เท่านั้น ความแตกต่างนี้สำคัญมาก เพราะการแก้ error ตอน build (เช่นแก้ syntax ผิด) ไม่ถือว่าเป็น "debugging" ตามความหมายที่จะใช้ตลอด Part นี้

33.2 Testing, Debugging, Exception Handling ต่างกันอย่างไร

การทดสอบ (Testing) — หน้าที่ของนักพัฒนา

การพัฒนาซอฟต์แวร์เกี่ยวข้องกับการทดสอบจำนวนมาก จนกลายเป็นสายงานเฉพาะทาง (software tester) และมีแนวทางพัฒนาที่ยึดการทดสอบเป็นศูนย์กลาง เช่น test-driven development การทดสอบแบ่งกว้างๆ ได้เป็นสองหมวด:

หมวดตัวอย่างชนิดย่อย
Functional — ทดสอบว่าทำงานตรงตามฟังก์ชันที่ออกแบบไว้ unit testing · integration testing · system testing · acceptance testing
Nonfunctional — ทดสอบด้านอื่นนอกเหนือจากฟังก์ชันการทำงาน security testing · performance testing · usability testing · compatibility testing

นักพัฒนาส่วนใหญ่ไม่ได้มองตัวเองเป็น "tester" แต่ก็ยังมีหน้าที่ทดสอบระดับหนึ่งอยู่เสมอ ก่อนส่งงานต่อ — โดยมากจะอยู่ในระดับ unit testing (ทดสอบหน่วยเล็กๆ ของโค้ดที่ตัวเองเขียน)

การดีบัก (Debugging) — ไม่ใช่แค่แก้ syntax

debugging คือกระบวนการที่นักพัฒนาใช้ "หาสาเหตุ" และ "แก้ไข" ปัญหาในโค้ด ปัญหานั้น อาจเกี่ยวกับ logic ของโค้ดหรือเกี่ยวกับ exception ก็ได้ คำว่า debugging มักสงวนไว้สำหรับ ปัญหาตอน runtime ที่หาสาเหตุได้ไม่ง่าย — การแก้ syntax error ทั่วไป เช่น ลืม ; ท้ายบรรทัด จึงไม่นับว่าเป็นการ debug ตามปกติ

ลองดูโค้ดตัวอย่างนี้:

Program.cs 
string[] students = new string[] {"Sophia", "Nicolas", "Zahirah", "Jeong"};

int studentCount = students.Length;

Console.WriteLine("ชื่อสุดท้ายคือ: " + students[studentCount]);

โค้ดนี้ตั้งใจจะ: ประกาศ array ชื่อ students เก็บชื่อนักเรียน, ประกาศตัวแปร studentCount ด้วยค่าจาก Length, แล้วพิมพ์ชื่อนักเรียนคนสุดท้าย ออกทางคอนโซล มองผ่านๆ ดูเหมือนไม่มีอะไรผิด แต่โค้ดนี้จะเกิด exception ตอนรันบรรทัด สุดท้าย เพราะ array นับ index จาก 0 — ชื่อสุดท้ายจริงๆ อยู่ที่ students[studentCount - 1] ไม่ใช่ students[studentCount] (ทบทวน zero-based index ได้ที่ บทที่ 10)

ในตัวอย่างง่ายๆ แบบนี้คุณอาจสังเกตเห็นปัญหาได้ทันที แต่ในโค้ดที่ซับซ้อนกว่านี้มาก การหา ต้นตอปัญหาไม่ใช่เรื่องง่ายเสมอไป — นั่นคือเหตุผลที่ต้องมีเครื่องมือและวิธีการที่เป็นระบบ เข้ามาช่วย ซึ่งจะพูดถึงในหัวข้อถัดไป

การจัดการ Exception (Exception Handling) — เผื่อไว้ตอน runtime

ถ้าแอปพลิเคชันสร้าง exception ขึ้นมา และ exception นั้นไม่ถูกจัดการในโค้ด แอปจะแสดง ข้อผิดพลาดแล้วปิดตัวเอง การจัดการ exception เป็นความรับผิดชอบของนักพัฒนาโดยตรง C# มีวิธีให้ "ลอง (try)" รันโค้ดที่รู้ว่าอาจเกิด exception ได้ และ "ดัก (catch)" exception ที่เกิดขึ้นจริง — รายละเอียดเต็มเรื่อง try-catch จะอยู่ใน บทที่ 35

Check ★ ข้อผิดพลาดแบบไหนที่เรียกว่า "exception" ตามนิยามในบทนี้?

  • Aลืมพิมพ์เซมิโคลอน ; ท้ายบรรทัด
  • Bโค้ดเข้าถึง index ของ array ที่ไม่มีอยู่จริงตอนแอปกำลังรัน
  • Cพิมพ์ชื่อ method ผิดจนคอมไพล์ไม่ผ่าน
เฉลย: ข้อ B. ข้อ A และ C เป็น error ที่เกิดตอน build/compile ไม่ใช่ exception ส่วนข้อ B เกิดขึ้นระหว่างแอปกำลังรัน จึงเข้านิยาม exception

Check ★ ใครมีหน้าที่รับผิดชอบการทดสอบซอฟต์แวร์?

  • Aนักพัฒนาเท่านั้น
  • Bsoftware tester เท่านั้น
  • Cทั้งนักพัฒนาและ tester — นักพัฒนายังต้องทำ unit testing ระดับหนึ่งเสมอ
เฉลย: ข้อ C. แม้ tester มืออาชีพจะรับผิดชอบการทดสอบส่วนใหญ่ในทีมใหญ่ แต่นักพัฒนาก็ยังมีหน้าที่ทดสอบงานของตัวเองระดับ unit testing ก่อนส่งต่อเสมอ

33.3 Debugger คืออะไร ทำไมดีกว่าอ่านโค้ดเอง

เจอบั๊กแล้วอยากแก้เร็วๆ เป็นเรื่องธรรมชาติ วิธี "มือสมัครเล่น" ที่มักถูกลองก่อนมีสามแบบ:

  • อ่านโค้ดซ้ำไปซ้ำมา หวังว่ารอบนี้จะเห็นปัญหา
  • แปะ Console.WriteLine("here") ไล่เป็นจุดๆ เพื่อดูว่าโค้ดวิ่งมาถึงไหน
  • รันแอปซ้ำด้วยข้อมูลชุดต่างๆ แล้วเดาจากที่เห็นว่าอะไรทำงาน อะไรไม่ทำงาน

วิธีเหล่านี้อาจได้ผลบ้างในกรณีง่ายๆ แต่ไม่ scale เมื่อบั๊กซับซ้อนขึ้น วิธีที่ได้รับการ ยอมรับว่าได้ผลที่สุดคือการใช้ debugger

debugger คือเครื่องมือซอฟต์แวร์ที่ใช้สังเกตและควบคุม "การไหลของการทำงาน" ของโปรแกรมด้วยวิธีที่เป็นระบบ ช่วยแยกหาสาเหตุของบั๊กและช่วยแก้ไขได้ debugger เชื่อมต่อ กับโค้ดได้สองแบบ: (1) โฮสต์โปรแกรมของคุณไว้ในโปรเซสของตัวมันเอง หรือ (2) รันเป็นโปรเซส แยกต่างหากที่ "แนบ" (attach) เข้ากับโปรแกรมที่กำลังรันอยู่แล้ว debugger มีทั้งแบบ command line และแบบมี GUI — Visual Studio Code มี debugger ผนวกอยู่ในตัว UI เลย (จะได้ลองใช้จริงในบทที่ 34)

ทุก debugger มีฟีเจอร์หลักที่สำคัญที่สุดสองอย่างเหมือนกัน:

  • ควบคุมการทำงาน (control execution) — pause โปรแกรมและรันทีละบรรทัดได้ ทำให้เห็นว่าโค้ดส่วนไหนถูกรันจริง และมันส่งผลต่อสถานะโปรแกรมอย่างไร
  • สังเกตสถานะ (observe state) — ดูค่าของตัวแปรและพารามิเตอร์ ณ จุดใดก็ได้ ระหว่างการรัน

การใช้ debugger เก่งเป็นทักษะสำคัญที่นักพัฒนามักมองข้าม การใช้ debugger อย่างมี ประสิทธิภาพช่วยให้ตามหาบั๊กได้เร็วขึ้น และยังช่วยให้เข้าใจว่าโปรแกรมทำงานอย่างไรจริงๆ ด้วย ไม่ใช่แค่ตอนมีบั๊กเท่านั้น

Check ★ ข้อใดอธิบาย "debugger" ได้ถูกต้องที่สุด?

  • Aโปรแกรมที่เขียนโค้ดให้อัตโนมัติตามที่ผู้ใช้สั่ง
  • Bเครื่องมือซอฟต์แวร์ที่สังเกตและควบคุมการไหลของการทำงานของโปรแกรม
  • Cเครื่องมือที่ช่วยเขียนโค้ดให้เร็วขึ้นด้วย autocomplete
เฉลย: ข้อ B. debugger ไม่ได้เขียนหรือแก้โค้ดให้อัตโนมัติ แต่ช่วยให้คุณ "เห็น" และ "ควบคุม" การทำงานของโปรแกรมแบบละเอียดขึ้น

33.4 Exception คืออะไร: แนวคิด throw และ catch

นิยามที่เป็นทางการของ exception ใน C#: ข้อผิดพลาดตอน runtime ถูกส่งผ่านโปรแกรมด้วยกลไก ที่เรียกว่า exception — exception ถูก "throw" (โยน) โดยโค้ดที่เจอปัญหา และถูก "catch" (ดัก) โดยโค้ดที่สามารถแก้ไขปัญหานั้นได้ exception อาจถูกโยนโดย .NET runtime เองหรือโดยโค้ดในโปรแกรมก็ได้ และแทนด้วยคลาสที่สืบทอดมาจากคลาส Exception — แต่ละคลาสจะระบุชนิดของ exception และมี property เก็บ รายละเอียดของปัญหานั้นไว้

ไม่ต้องเข้าใจเรื่องคลาสแบบลึกซึ้งก็ใช้ exception ได้ — ลองมองว่า exception คือ "ตัวแปร พิเศษ" ที่มีความสามารถเพิ่มเติม: สร้าง exception ได้หลายชนิด และเข้าถึงเนื้อหาข้างในของ มันได้เหมือนตัวแปรทั่วไป

สรุปเป็นภาษาคน: เมื่อโค้ดของคุณเจอปัญหาตอนรัน .NET runtime (หรือโค้ดของคุณเอง) จะ "โยน" exception ออกมา ถ้ามี catch ดักไว้ โค้ดในนั้นจะอ่านรายละเอียดจาก exception แล้วดำเนินการแก้ไขสถานการณ์ได้ แต่ถ้าไม่มี catch ดักไว้เลย (unhandled exception) แอปจะแสดงข้อผิดพลาดแล้วปิดตัวลงทันที

ถ้าไม่มีกล่อง "catch" ดักไว้ตรงปลายทาง — คือไม่มีใครรับ exception นั้นเลย — แอปจะพัง และปิดตัวลงทันทีแทน นี่คือเหตุผลที่ Part นี้ทั้ง Part มีอยู่: เพื่อให้คุณเขียนโค้ดที่ "ดัก" ปัญหาไว้ก่อนที่มันจะทำให้แอปทั้งตัวล่ม

33.5 ⚠️ กับดักที่พบบ่อย / เข้าใจผิดบ่อย

ความเข้าใจผิดความจริง
แก้ลืมเซมิโคลอนแล้วนับว่า "กำลัง debug" นั่นคือการแก้ syntax error ตอน build — คำว่า debugging สงวนไว้สำหรับปัญหาตอน runtime ที่หาสาเหตุได้ไม่ง่าย
คิดว่า "รันได้ไม่มี error สีแดง" แปลว่าเทสผ่านแล้ว build/run ผ่านไม่ได้แปลว่า logic ถูกต้อง — ต้องตรวจผลลัพธ์เทียบกับที่ควรจะเป็นด้วย (นี่คืองานของ testing จริงๆ)
คิดว่าแปะ Console.WriteLine("here") หลายจุดคือวิธี debug ที่ดีที่สุด ใช้ได้ในกรณีง่ายๆ แต่ไม่ scale ต้องคอยลบทิ้งภายหลัง และไม่เห็นค่าตัวแปรแบบละเอียด เท่า debugger
คิดว่า error ตอน build กับ exception ตอน runtime เป็นเรื่องเดียวกัน error ตอน build (เช่น syntax ผิด) ไม่ใช่ exception — exception เกิดเฉพาะตอนแอป กำลังรันเท่านั้น
คิดว่าทุก exception ต้อง catch เสมอไม่งั้นผิด การ catch เป็นทางเลือกที่ควรทำเมื่อ "แก้ไขสถานการณ์ได้จริง" — ถ้าไม่ catch .NET runtime จะปล่อยให้แอปปิดตัวเอง (unhandled) ซึ่งบางครั้งก็เป็นพฤติกรรมที่ ยอมรับได้สำหรับข้อผิดพลาดร้ายแรงจริงๆ

  • Bแอปพลิเคชันแสดงข้อผิดพลาดแล้วปิดตัว

2. วิธีใดคือแนวทางที่ดีที่สุดในการหาสาเหตุที่แท้จริง (root cause) ของบั๊ก?

  • Aรันแอปซ้ำด้วยข้อมูลชุดต่างๆ ไปเรื่อยๆ แล้วเดา
  • Bแปะ Console.WriteLine("here") ไล่ทีละจุดในโค้ด
  • Cใช้ debugger สังเกตและควบคุมการทำงานของโปรแกรม
เฉลย: ข้อ C. ทั้งข้อ A และ B เป็นวิธีที่ใช้ได้ในสถานการณ์ง่ายๆ แต่ไม่แม่นยำและไม่ scale เท่าการใช้ debugger ซึ่งให้คุณเห็นสถานะจริงของโปรแกรม ณ จุดใดก็ได้

33.7 ✍️ แบบฝึกหัดท้ายบท

ข้อ 1ง่าย

โค้ดต่อไปนี้ตั้งใจพิมพ์ผลไม้ชิ้นสุดท้ายในรายการ แต่จะเกิด exception ตอนรัน — หา สาเหตุและแก้ไข

Program.cs
string[] fruits = new string[] {"มะม่วง", "กล้วย", "ส้ม"};
int count = fruits.Length;
Console.WriteLine("ผลไม้ชิ้นสุดท้าย: " + fruits[count]);
💡 คำใบ้

array นับ index จาก 0 — ชิ้นสุดท้ายไม่ได้อยู่ที่ index เท่ากับ Length

ดูเฉลย
Program.cs
Console.WriteLine("ผลไม้ชิ้นสุดท้าย: " + fruits[count - 1]);
ข้อ 2ง่าย

จำแนกสถานการณ์ทดสอบต่อไปนี้ว่าเป็น Functional หรือ Nonfunctional testing:

(1) เช็คว่าปุ่ม "เข้าสู่ระบบ" พาไปหน้าถัดไปถูกต้อง   (2) เช็คว่าหน้าเว็บโหลดเสร็จภายใน 2 วินาที   (3) เช็คว่าแอปใช้งานได้ทั้งบน Windows และ macOS   (4) เช็คว่าเมธอดคำนวณส่วนลดคืนค่าถูกต้อง

ดูเฉลย

(1) Functional — ทดสอบว่าฟังก์ชันทำงานถูกต้อง
(2) Nonfunctional (performance testing)
(3) Nonfunctional (compatibility testing)
(4) Functional — ทดสอบ logic ของเมธอด

ข้อ 3กลาง

โค้ดต่อไปนี้จะเกิด exception ตอนรัน — บอกว่าเกิดจากอะไร และถ้าไม่มีการจัดการ (unhandled) จะเกิดอะไรขึ้นกับแอป

Program.cs
int total = 100;
int people = 0;
Console.WriteLine("เฉลี่ยคนละ: " + (total / people));
ดูเฉลย

เกิดจากการหารด้วยศูนย์ (people มีค่า 0) ซึ่งเป็นการดำเนินการที่ ไม่มีผลลัพธ์ทางคณิตศาสตร์ที่ถูกต้อง .NET runtime จะ throw exception ออกมาตอนรัน บรรทัดนี้ ถ้าไม่มี catch ดักไว้เลย แอปจะแสดงข้อผิดพลาดแล้วปิดตัวลง ทันที (รายละเอียดเรื่อง try-catch จริงจะได้เรียนในบทที่ 35)

ข้อ 4กลาง

อธิบายด้วยคำพูดตัวเอง (2-3 ประโยค) ว่าทำไมการใช้ debugger ถึงดีกว่าการแปะ Console.WriteLine("here") ไล่ทีละจุดในโค้ด

ดูแนวคำตอบ

แนวคำตอบตัวอย่าง: debugger ให้คุณ pause โปรแกรม ณ จุดใดก็ได้ แล้วดูค่าจริงของ ตัวแปรทุกตัวพร้อมกัน โดยไม่ต้องแก้โค้ดเพิ่มหรือคอยลบทิ้งภายหลัง ต่างจากการแปะ Console.WriteLine ที่บอกได้แค่ว่า "โค้ดวิ่งมาถึงจุดนี้หรือยัง" แต่ไม่เห็นภาพรวมของสถานะโปรแกรมทั้งหมดในเวลาเดียวกัน และยิ่งบั๊กซับซ้อนขึ้น ก็ยิ่งต้องแปะเพิ่มเรื่อยๆ จนโค้ดรก

ข้อ 5ท้าทาย

แอปคำนวณดอกเบี้ยธนาคารง่ายๆ รับเงินต้นและอัตราดอกเบี้ยจากผู้ใช้ แล้วคำนวณดอกเบี้ย รวมออกมา ระบุว่าสถานการณ์ต่อไปนี้ควรใช้ "debugger หา logic ที่ผิด" หรือ "เขียน exception handling ดักไว้" — พร้อมเหตุผลสั้นๆ:

(1) สูตรคำนวณดอกเบี้ยให้ผลลัพธ์ผิดทุกครั้งที่เงินต้นเป็นทศนิยม   (2) ผู้ใช้พิมพ์ตัวอักษรแทนตัวเลขตอนกรอกเงินต้น

ดูแนวคำตอบ

(1) ควรใช้ debugger — นี่คือปัญหา logic ในสูตรคำนวณของเราเอง ต้อง step ผ่านโค้ดทีละบรรทัดเพื่อดูว่าค่าทศนิยมถูกคำนวณหรือแปลงผิดตรงไหน
(2) ควรใช้ exception handling — นี่คือข้อผิดพลาดที่มาจาก "ข้อมูลนำเข้าจาก ผู้ใช้" ตอน runtime ซึ่งเราควบคุมไม่ได้ล่วงหน้า ต้องเขียนโค้ดดักไว้ (try-catch) เพื่อแจ้งเตือนผู้ใช้อย่างสุภาพแทนที่จะปล่อยให้แอปพัง

📌 สรุปบทที่ 33

บทนี้ปูพื้นฐานสามแนวคิดที่นักพัฒนา C# ต้องเจอตลอดอาชีพ: testing ตรวจสอบว่าโค้ด ทำงานถูกต้องตามที่ออกแบบไว้ (ทั้งเชิงฟังก์ชันและไม่ใช่ฟังก์ชัน) debugging คือ กระบวนการหาสาเหตุและแก้ไขปัญหาที่เกิดตอน runtime ซึ่งใช้ debugger เป็นเครื่องมือ หลักในการควบคุมและสังเกตการทำงานของโปรแกรม และ exception handling คือการเตรียม รับมือข้อผิดพลาดที่เกิดตอนแอปกำลังรัน ด้วยกลไก throw/catch

ทั้งสามแนวคิดนี้เกี่ยวข้องกันแต่ไม่ใช่สิ่งเดียวกัน และเป็นความรับผิดชอบของนักพัฒนา โดยตรงทั้งหมด บทถัดไปคุณจะได้ลงมือใช้เครื่องมือ debugger จริงของ Visual Studio Code ก่อนที่จะไปเขียน try-catch จัดการ exception จริงในบทที่ 35-36
