34.1 หน้าตาของ RUN AND DEBUG view

VS Code มีส่วนติดต่อผู้ใช้หลายจุดที่ช่วยตั้งค่า เริ่ม และควบคุม debug session — มาทำความ รู้จักทีละส่วนก่อนลงมือจริง

เมนู Run

เมนู Run บนแถบเมนูของ VS Code รวมคำสั่งที่ใช้บ่อยไว้ 6 หมวด:

หมวดใช้ทำอะไร
Start / Stop Debuggingเริ่ม-หยุดรันโค้ด ทั้งแบบมีและไม่มี debugger แนบอยู่
Launch configurationsเปิดดูหรือสร้าง launch configuration (ไฟล์ launch.json)
Runtime controlสั่งเดินหน้าโค้ดระหว่าง execution ถูก pause อยู่
Set Breakpointsสลับเปิด/ปิด breakpoint บนบรรทัดโค้ดที่ cursor อยู่
Manage Breakpointsจัดการ breakpoint ทีเดียวหลายจุด (enable/disable/remove ทั้งหมด)
Install Debuggersเปิดหน้า EXTENSIONS กรองเฉพาะ debugger

ส่วนต่างๆ ของ RUN AND DEBUG view

เปิด RUN AND DEBUG view ได้จากไอคอนรูป "▷ กับจุดบัค" บน Activity Bar ด้านซ้าย ภายในมี ส่วนสำคัญดังนี้:

ส่วนหน้าที่
Controls panelปุ่ม Start Debugging (▶ สีเขียว) + dropdown เลือก launch configuration + ปุ่มเฟือง (เปิด launch.json) + ปุ่ม ⋯ (ซ่อน/แสดง ส่วนต่างๆ)
VARIABLESดูและจัดการค่าตัวแปรระหว่าง debug session
WATCHเฝ้าดูตัวแปรหรือ expression ที่กำหนดเอง เช่น ตั้ง watch ไว้ดูว่าเมื่อไหร่เงื่อนไขหนึ่งจะเป็นจริง
CALL STACKติดตามตำแหน่งการทำงานปัจจุบัน ตั้งแต่จุดเริ่มเข้าแอป — บอกว่าตอนนี้อยู่ใน method ไหน และ method ไหนเรียกมันมาบ้าง
BREAKPOINTSแสดงรายการ breakpoint ที่ตั้งไว้ทั้งหมด
Debug toolbarแถบควบคุมการรัน แสดงเฉพาะตอนแอปกำลังรันอยู่
DEBUG CONSOLEแสดงข้อความจาก debugger — เป็นคอนโซลเริ่มต้นของ console app แสดงผลจาก Console.WriteLine() ได้ด้วย

Debug toolbar — 6 ปุ่มควบคุมการรัน

ปุ่มทำอะไร
Pause / Continueหยุดการทำงานชั่วคราวตอนกำลังรัน หรือรันต่อ ตอนถูก pause อยู่
Step Overรัน method ถัดไปเป็นก้อนเดียว โดยไม่ลงไปดูข้างในทีละ บรรทัด
Step Intoเข้าไปในบรรทัด/method ถัดไป เพื่อดูการทำงานทีละบรรทัด ข้างใน
Step Outถ้ากำลังอยู่ใน method ให้รันทุกบรรทัดที่เหลือของ method นั้นรวดเดียว แล้วกลับไปจุดที่เรียกมัน
Restartยกเลิกการรันปัจจุบัน แล้วเริ่ม debug session ใหม่ด้วย configuration เดิม
Stopยกเลิกการรันปัจจุบันทั้งหมด

Check ★ ส่วนใดของ RUN AND DEBUG view ใช้ติดตามตำแหน่งการทำงานปัจจุบันของโปรแกรม ตั้งแต่จุดเริ่มเข้าแอป?

  • AVARIABLES section
  • BCALL STACK section
  • CWATCH section
เฉลย: ข้อ B. CALL STACK แสดงว่าตอนนี้กำลังอยู่ใน method ไหน และ method ไหนเรียกต่อกันมาจนถึงจุดปัจจุบัน ส่วน VARIABLES ดูค่าตัวแปร และ WATCH เฝ้าดู expression ที่ตั้งเอง

34.2 ลงมือ: รันโค้ดในโหมด Debug ครั้งแรก

เตรียมโปรเจกต์

Terminal 
dotnet new console -o ch34-debugger

เปิดโฟลเดอร์ ch34-debugger ด้วย VS Code แล้วแทนที่เนื้อหาใน Program.cs ด้วยโค้ดนี้:

Program.cs 
int score = 0;

for (int round = 1; round <= 3; round++)
{
    score += round * 10;
    Console.WriteLine($"รอบที่ {round}: คะแนนสะสม {score}");
}

Console.WriteLine($"คะแนนรวมสุดท้าย: {score}");

ตั้ง breakpoint บนบรรทัด score += round * 10; โดยคลิกที่ช่องว่างด้านซ้าย ของเลขบรรทัดนั้น (จะมี "จุดสีแดง" ขึ้นมา) จากนั้นเปิด RUN AND DEBUG view แล้วกด Start Debugging (หรือกด F5)

โปรแกรมจะรันไปหยุดที่ breakpoint พอดี — สังเกตส่วน VARIABLES ทางซ้าย จะเห็นค่าปัจจุบัน ของ score และ round ตอนนั้น ลองกด Step Over ดูหลายๆ ครั้ง แล้วสังเกตว่าค่า score เปลี่ยนไปทีละรอบตามที่คาดไว้ไหม จากนั้นกด Continue ให้โปรแกรมรันจนจบ

Check ★ ปุ่มใดบน Debug toolbar ใช้ "รันต่อ" หลังจากโค้ดถูก pause ไว้ที่ breakpoint?

  • APause / Continue
  • BStep Over
  • CRestart
เฉลย: ข้อ A. ปุ่มเดียวกันสลับหน้าที่ตามสถานะ: Pause ตอนกำลังรัน และ Continue ตอนถูก pause อยู่ — Step Over รันทีละก้อนโค้ด ไม่ใช่ "รันต่อจนจบหรือจน breakpoint ถัดไป"

34.3 ตั้งค่า Breakpoint: Set / Remove / Disable / Enable

ตั้ง breakpoint ได้สองทาง: คลิกที่ช่องด้านซ้ายของเลขบรรทัดใน Editor หรือใช้คำสั่ง Toggle Breakpoint จากเมนู Run (ใช้กับบรรทัดที่ cursor อยู่) เมื่อโค้ดรันมาถึง breakpoint การทำงานจะหยุดพัก

ลบ breakpoint ได้โดยทำซ้ำวิธีเดิมที่ใช้ตั้งมัน (คลิกจุดแดงอีกครั้ง หรือ Toggle Breakpoint ซ้ำ) แต่ถ้าอยากเก็บตำแหน่ง breakpoint ไว้แต่ไม่ให้ทำงานรอบนี้ ให้ "ปิดใช้งาน (disable)" แทนการลบ — คลิกขวาที่จุดแดง แล้วเลือก Disable Breakpoint จุดจะเปลี่ยนจากสีแดงเป็นสีเทา

นอกจากจัดการทีละจุด เมนู Run ยังมีคำสั่งจัดการทั้งหมดพร้อมกัน:

  • Enable All Breakpoints — เปิดใช้งาน breakpoint ที่ถูกปิดไว้ทั้งหมด
  • Disable All Breakpoints — ปิดใช้งาน breakpoint ทั้งหมด
  • Remove All Breakpoints — ลบ breakpoint ทั้งหมด (ทั้งที่เปิดและปิดใช้งานอยู่)

34.4 Breakpoint แบบมีเงื่อนไข, Hit Count และ Logpoint

Conditional breakpoint คือ breakpoint พิเศษที่หยุดโค้ดเฉพาะเมื่อเงื่อนไขที่ กำหนดเป็นจริงเท่านั้น ตั้งได้โดยคลิกขวา (ไม่ใช่คลิกซ้าย) ที่ช่องด้านซ้ายเลขบรรทัด แล้วเลือก Add Conditional Breakpoint — หรือคลิกขวาที่ breakpoint ที่มีอยู่แล้ว เลือก Edit Breakpoint เพื่อเปลี่ยนมันให้มีเงื่อนไข

ทุกครั้งที่ debugger เจอ conditional breakpoint จะประเมิน expression ที่กำหนดไว้ — ถ้า ได้ true จะหยุด ถ้าได้ false จะข้ามไปเหมือนไม่มี breakpoint เลย เช่น ถ้ากำลัง debug โค้ดข้างใน for loop และสงสัยว่าปัญหาเกิดหลัง วนไปแล้วหลายรอบ ก็ตั้งเงื่อนไขเป็น round > 2 — debugger จะข้าม breakpoint ไปจนกว่า round จะมากกว่า 2 จริงๆ ถึงจะหยุด

C# debugger ของ VS Code ยังรองรับสองแบบเพิ่มเติม:

  • Hit Count breakpoint — กำหนดจำนวนครั้งที่ breakpoint ต้องถูกเจอ ก่อนจะ "หยุด" จริงๆ (เช่นตั้งไว้ 5 ก็จะหยุดเฉพาะครั้งที่ 5)
  • Logpoint — breakpoint ที่ "ไม่หยุด" การทำงาน แต่พิมพ์ข้อความ log ออกไปแทน มีประโยชน์มากตอน debug ระบบที่ pause ไม่ได้ (เช่นระบบ production) หน้าตาเป็นไอคอน รูป "เพชร" แทนวงกลมทึบ ข้อความ log เป็นข้อความธรรมดาแต่ใส่ expression ในวงเล็บปีกกา {} ได้ เช่น round = {round} ผสมกับเงื่อนไข hit count >4 ก็จะได้ log เฉพาะตั้งแต่ครั้งที่ 5 เป็นต้นไป

Check ★ conditional breakpoint คืออะไร?

  • Abreakpoint ที่หยุดการทำงานเฉพาะเมื่อเงื่อนไขที่กำหนดเป็นจริง
  • Bbreakpoint ที่หยุดทุกครั้งที่รันโค้ด ไม่มีข้อยกเว้น
  • Cbreakpoint ที่มองเห็นได้เฉพาะใน Editor แต่ไม่มีผลต่อการ debug จริง
เฉลย: ข้อ A. ต่างจาก breakpoint ปกติที่หยุดทุกครั้งไม่มีเงื่อนไข — conditional breakpoint จะประเมิน expression ก่อน หยุดเฉพาะตอนได้ true

34.5 ไฟล์ launch.json: ตั้งค่าการรันดีบักเอง

VS Code ใช้ไฟล์ launch.json (อยู่ในโฟลเดอร์ .vscode) เก็บ ค่า config ของ debugger สำหรับโปรเจกต์ console แบบง่ายๆ VS Code มักสร้างไฟล์นี้ให้ อัตโนมัติจนครบพร้อมใช้เลย แต่บางสถานการณ์ก็ต้องแก้เอง — ควรรู้จัก attribute หลักๆ ไว้

ไฟล์ launch.json มี list ชื่อ configurations แต่ละ configuration ต้องมี 3 attribute นี้เสมอ:

Attributeความหมาย
nameชื่อที่อ่านง่ายของ configuration นี้ — ไปโผล่ใน dropdown เลือก configuration
typeชนิดของ debugger — สำหรับแอป .NET/C# ใช้ค่า coreclr
requestชนิดคำขอ — รองรับ launch (เปิดโปรแกรม ใหม่) กับ attach (แนบเข้าโปรเซสที่รันอยู่แล้ว)

attribute อื่นๆ ที่พบบ่อย:

Attributeความหมาย
preLaunchTaskชื่อ task ที่ต้องรันก่อน debug (นิยามใน tasks.json) — ปกติตั้งเป็นงาน dotnet build
programpath ไปยังไฟล์ .dll ที่จะรัน รูปแบบทั่วไปคือ ${workspaceFolder}/bin/Debug/<target-framework>/<ชื่อโปรเจกต์>.dll
cwdworking directory ของโปรเซสเป้าหมาย
argsargument ที่ส่งให้โปรแกรมตอนเริ่มรัน (ค่าเริ่มต้นคือ ไม่มี)
consoleชนิดคอนโซลที่ใช้รัน — internalConsole (ค่าเริ่มต้น), integratedTerminal, หรือ externalTerminal
stopAtEntryตั้งเป็น true ถ้าอยากให้หยุด ที่จุดเริ่มต้นโปรแกรมทันที
⚠️ กับดักสำคัญ: แอปที่มี Console.ReadLine() debug ไม่ได้ถ้าใช้ค่า default แผง DEBUG CONSOLE (ค่า console เริ่มต้น internalConsole) ไม่รองรับ การรับ input จากผู้ใช้ — ถ้าโปรเจกต์ของคุณมี Console.ReadLine() (เช่นแอป Contoso Pets ในบทที่ 19 หรือสวนสัตว์เลี้ยงในบทที่ 31) ต้องแก้ค่า console ใน launch.json เป็น integratedTerminal หรือ externalTerminal ก่อน ไม่งั้น debug session จะค้างหรือรับค่าไม่ได้

อีกสถานการณ์ที่ต้องแก้ไฟล์เอง คือเวิร์กスペースมีมากกว่าหนึ่งโปรเจกต์ที่รันได้ — ต้อง สร้าง configuration แยกให้แต่ละแอป พร้อม preLaunchTask ของตัวเองใน tasks.json ตัวอย่างเช่น เวิร์กスペースชื่อ SpecialProjects ที่มีสองแอปคือ Project123 และ Project456:

.vscode/launch.json
"configurations": [
    {
        "name": "Launch Project123",
        "type": "coreclr",
        "request": "launch",
        "preLaunchTask": "buildProject123",
        "program": "${workspaceFolder}/Project123/bin/Debug/net10.0/Project123.dll",
        "cwd": "${workspaceFolder}/Project123",
        "console": "internalConsole"
    },
    {
        "name": "Launch Project456",
        "type": "coreclr",
        "request": "launch",
        "preLaunchTask": "buildProject456",
        "program": "${workspaceFolder}/Project456/bin/Debug/net10.0/Project456.dll",
        "cwd": "${workspaceFolder}/Project456",
        "console": "internalConsole"
    }
]

เมื่อตั้งค่าครบ dropdown บน Controls panel ของ RUN AND DEBUG view จะให้เลือกได้ว่าจะ debug แอปไหน

Check ★ ต้องแก้ attribute ไหนใน launch.json ถ้าแอป console ของคุณมี Console.ReadLine() รับ input จากผู้ใช้?

  • Aprogram
  • BpreLaunchTask
  • Cconsole — เปลี่ยนเป็น integratedTerminal หรือ externalTerminal
เฉลย: ข้อ C. ค่าเริ่มต้น internalConsole (DEBUG CONSOLE) ไม่รองรับ input — ต้องเปลี่ยนเป็น integratedTerminal หรือ externalTerminal เพื่อให้ Console.ReadLine() ทำงานได้ตอน debug

34.6 ลงมือ: ติดตามตัวแปรด้วย VARIABLES, WATCH, CALL STACK

ลองเขียนโค้ดนี้ทับ Program.cs เดิม เป็นเมธอดคำนวณราคาสินค้าหลังลด แล้ว ตั้งใจ debug หาว่าทำไมราคาสุดท้ายไม่ตรงกับที่คาด:

Program.cs 
decimal price = 250m;
decimal discountRate = 0.1m;

decimal finalPrice = ApplyDiscount(price, discountRate);

Console.WriteLine($"ราคาสุทธิ: {finalPrice:C}");

decimal ApplyDiscount(decimal original, decimal rate)
{
    decimal discount = original * rate;
    decimal result = original - discount;
    return result;
}

ตั้ง breakpoint บนบรรทัด decimal discount = original * rate; แล้วเริ่ม debug (F5) — เมื่อโปรแกรมหยุดตรง breakpoint:

  • ดูที่ VARIABLES — จะเห็นค่า original และ rate ที่ method นี้ได้รับมา
  • เพิ่ม expression original - discount ลงใน WATCH — VS Code จะ คำนวณและแสดงผลให้แบบสด แม้ discount ยังไม่ถูกคำนวณ (ตอนนั้นอาจขึ้น error ชั่วคราว จนกว่าจะ step ผ่านบรรทัดที่กำหนดค่าให้)
  • ดูที่ CALL STACK — จะเห็นว่าตอนนี้กำลังอยู่ใน ApplyDiscount ซึ่งถูกเรียกมาจาก scope หลักของโปรแกรม (แสดงลำดับการเรียกจากบนลงล่าง)
  • กด Step Over ผ่านทั้งสองบรรทัดในเมธอด แล้วสังเกตค่าใน WATCH และ VARIABLES อัปเดตตามจริง
  • กด Step Out เพื่อกลับไปยังจุดที่เรียก ApplyDiscount ทันที

เทคนิคนี้เป็นหัวใจของการ debug จริง: ตั้ง breakpoint ใกล้จุดที่สงสัย แล้วใช้ VARIABLES + WATCH + CALL STACK ยืนยันว่าค่าที่ได้ตรงกับที่คาดไว้ทุกขั้นตอนหรือไม่ — พอเจอจุดที่ ค่าเริ่ม "ผิดไปจากที่ควรจะเป็น" นั่นแหละคือจุดเกิดบั๊ก

อาการสาเหตุ / วิธีแก้
กด F5 แล้วโปรแกรมรันจบเลย ไม่หยุดที่ breakpoint เช็คว่าจุดแดงยังอยู่ที่บรรทัดนั้นจริง (ไม่ได้เผลอปิด/ลบ) และเช็คว่ากำลังรันด้วย configuration ที่ตรงกับไฟล์ที่แก้ไข
Debug session ค้างตอนโปรแกรมควรจะรอรับ input console ใน launch.json ยังเป็น internalConsole — เปลี่ยน เป็น integratedTerminal หรือ externalTerminal
ตั้ง conditional breakpoint แล้วไม่เคยหยุดเลย expression อาจพิมพ์ผิด หรือเงื่อนไขไม่เคยเป็นจริงตามข้อมูลจริงที่ป้อนเข้าไป — ลองพิมพ์ expression เดียวกันใน WATCH ดูค่าจริงเทียบกัน
สับสนระหว่าง Step Over กับ Step Into Step Over = "ข้าม" รายละเอียดข้างในไปเลย (ใช้เมื่อมั่นใจว่า method นั้นไม่มีบั๊ก) · Step Into = "เดินเข้าไปดู" ทีละบรรทัดข้างใน (ใช้เมื่อสงสัย method นั้นเอง)
แก้โค้ดแล้วกด debug แต่พฤติกรรมเหมือนโค้ดเก่า ลืม build ใหม่ก่อน — เช็คว่า preLaunchTask ตั้งเป็นงาน build จริง หรือสั่ง dotnet build เองก่อน

34.8 ❓ Knowledge Check

คำถามชุดนี้แปลจาก Microsoft Learn (Check your knowledge ของแต่ละ unit)

1. attribute preLaunchTask ใน launch configuration ใช้ทำอะไร?

  • Aระบุ path ของไฟล์ .dll ที่จะรัน
  • Bระบุ task ที่ต้องรันก่อนเริ่ม debug โปรแกรม
  • Cระบุชนิดคอนโซลที่ใช้ตอนรันแอป
เฉลย: ข้อ B. preLaunchTask ชี้ไปยัง task ใน tasks.json (โดยทั่วไปคืองาน build) ที่ต้องรันให้เสร็จก่อน debugger จะ เริ่มทำงาน ส่วน program คือ path ของไฟล์ และ console คือ ชนิดคอนโซล

2. วิธีปิดใช้งาน (disable) breakpoint ใน VS Code ทำอย่างไร?

  • Aคลิกซ้ายที่จุดแดงหนึ่งครั้ง
  • Bคลิกขวาที่จุดแดง แล้วเลือก Disable Breakpoint
  • Cเลือก Remove Breakpoint จากเมนู Run
เฉลย: ข้อ B. คลิกซ้ายที่จุดแดงเป็นการ "ลบ" breakpoint ไม่ใช่ปิด ใช้งาน ส่วน Remove Breakpoint บนเมนู Run ก็คือการลบเช่นกัน — ต้องคลิกขวาแล้วเลือก Disable Breakpoint เท่านั้นถึงจะปิดใช้งานชั่วคราวโดยไม่ลบตำแหน่งทิ้ง

34.9 ✍️ แบบฝึกหัดท้ายบท

ข้อ 1กลาง

Variable state challenge (โจทย์ต้นฉบับจาก Microsoft Learn) — โค้ดต่อไปนี้ ตั้งใจจะเปลี่ยนค่า x เป็น 10 ผ่านเมธอด ChangeValue แล้ว พิมพ์ผลออกมา แต่ผลลัพธ์ที่ได้ไม่ตรงกับที่คาด — ใช้ breakpoint และ VARIABLES section หาสาเหตุ (ตั้ง breakpoint ที่บรรทัด int x = 5; แล้ว Step Into เข้าไปใน ChangeValue สังเกตค่า x ตลอดทาง)

Program.cs
int x = 5;

ChangeValue(x);

Console.WriteLine(x);

void ChangeValue(int value)
{
    value = 10;
}
💡 คำใบ้

สังเกตดีๆ ว่าค่า x เปลี่ยนไหมตอน execution เข้า-ออกจาก ChangeValue — ทบทวนเรื่อง pass-by-value ที่ บทที่ 29

ดูเฉลย

ค่า x ไม่เปลี่ยนเลยตลอดการ step เพราะ ChangeValue รับ ค่า (value) ของ x ไปเท่านั้น ไม่ใช่ตัวแปร x ตัวจริง — การแก้ value ข้างในเมธอดจึงไม่กระทบ x ที่เรียกมันมา ถ้าอยากให้ผลลัพธ์เปลี่ยนจริง ต้องให้เมธอดคืนค่ากลับมา แล้วนำไป assign ทับ:

Program.cs (แก้แล้ว)
int x = 5;
x = ChangeValue(x);
Console.WriteLine(x);

int ChangeValue(int value)
{
    value = 10;
    return value;
}
ข้อ 2ง่าย

เขียน array ของคะแนนสอบ int[] scores = {55, 82, 90, 61, 77}; ตั้ง conditional breakpoint บนบรรทัดที่พิมพ์ผลใน foreach loop ให้หยุด เฉพาะตอนคะแนนมากกว่า 80 เท่านั้น — เขียน expression ที่ต้องใส่ในเงื่อนไข

ดูเฉลย

ถ้าตัวแปร loop ชื่อ score เงื่อนไขที่ใส่ในกล่อง conditional breakpoint คือ score > 80 — debugger จะข้ามค่า 55, 61, 77 ไป และหยุด เฉพาะตอน score เป็น 82 กับ 90 เท่านั้น

ข้อ 3กลาง

โปรเจกต์ของคุณมี Console.ReadLine() รับชื่อผู้ใช้ แต่พอกด F5 เพื่อ debug แล้วโปรแกรมไม่ยอมรับการพิมพ์อะไรเลย ค้างอยู่แบบนั้น — ระบุว่าต้องแก้ไฟล์ไหน แก้ attribute อะไร และแก้เป็นค่าอะไร

ดูเฉลย

ต้องแก้ไฟล์ .vscode/launch.json เปลี่ยน attribute "console" จากค่าเริ่มต้น "internalConsole" เป็น "integratedTerminal" (หรือ "externalTerminal") เพราะ DEBUG CONSOLE (internalConsole) ไม่รองรับการรับ input จากผู้ใช้

📌 สรุปบทที่ 34

บทนี้พาคุณลงมือใช้เครื่องมือ debug ตัวจริงของ VS Code ครบทุกส่วนสำคัญ: RUN AND DEBUG view (VARIABLES, WATCH, CALL STACK, BREAKPOINTS), Debug toolbar (Pause/Continue, Step Over, Step Into, Step Out, Restart, Stop), การตั้ง/ลบ/ปิดใช้งาน breakpoint, breakpoint แบบมีเงื่อนไขและ logpoint, ไปจนถึงไฟล์ launch.json ที่ควบคุมพฤติกรรมการ debug ทั้งหมด

ทักษะเหล่านี้คือรากฐานของนักพัฒนาทุกคน — ยิ่งโค้ดซับซ้อนขึ้นเท่าไหร่ debugger ยิ่งช่วย คุณประหยัดเวลาได้มากขึ้นเท่านั้น เทียบกับการเดาหรือแปะ Console.WriteLine("here") ไล่ทีละจุดแบบที่พูดถึงในบทที่แล้ว บทถัดไปคุณจะเอาความรู้เรื่อง exception จากบทที่ 33 มา เขียนเป็นโค้ดจริงด้วย try-catch
